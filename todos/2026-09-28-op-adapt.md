## 目标

决定论文主方法的一个前提：openpilot 本身（不只是冻结特征上的 head）能不能被**便宜地**改到它的 vision 层，同时**不把它原来会的开车弄坏**。
第 42 条说行人信息在 openpilot 的 vision 层就被滤掉了（Cinque `vision` AUC 0.51）；第 44 条说 CARLA 激发的 head 加到冻结真实特征上有害。
用户选的改法是 B（vision 层后段部分解冻或 LoRA + 辅助 hazard loss + 对原输出蒸馏，保证正常驾驶不漂）或 C（全量微调）。
验收原则（用户）：真学会了就 sim 和 real 都能开，所以每个读数都要跨域。

名词：
- **port**：把 openpilot 的 ONNX 图逐节点翻成 PyTorch 算子（`op_torch.OnnxTorch`，图解释器），权重变成可训练参数，批量用 `torch.func.vmap`。
- **trunk**：Cinque vision 编码器里冻结不动的前段（ConvNeXt stem + stage 1–3，输出 `permute_73`，1024 × 8 × 16）。
- **stage 4**：vision 编码器最后一段（3 个 2048 通道 ConvNeXt block + 下采样 conv + LN + 1×1 投影到 32 × 512 的 hidden token `view_39`）。
- **policy**：Cinque 的时序部分，读当前与前 8 个 5 Hz hidden（1.6 s），出 `select_4`（= 我们一直用的 `temporal`）和 plan / lead 等全部输出。
- **蒸馏（distillation）**：让改过的模型在正常帧上的输出贴住原模型的输出。
- **漂移（drift）**：同一帧上改过的模型与原模型原生 plan 的差。

## B 小试的配置（跑之前写死）

- 可训练：Cinque stage 4 全解冻（约 1.1 亿参数，fp32 master、bf16 计算），其余（trunk、policy、所有输出头）冻结。trunk 输出按帧缓存。
- 辅助头（新加，可训练）：(i) 接 `select_4` 的 MLP 512→256→3；(ii) 接 32 个 hidden token 的 attention pooling → 3。
  三个输出：走廊内行人有无（主）、宽走廊内行人有无、最近走廊内行人的距离（只在正例上回归）。
- 行人标签（nuScenes keyframe，GT 框，`num_lidar_pts ≥ 1`）：走廊 = 第 44 / 53 条的定义（log 未来路径从原点起、沿末端朝向延长到 30 m，框中心或 4 个角 |d| ≤ 1.5 m 且 0 < s ≤ 30 m），
  类别 `human.pedestrian.*`；宽走廊 |d| ≤ 4 m、0 < s ≤ 40 m；距离 = 走廊内行人框中心到本车的最小欧氏距离。
- 蒸馏：原模型（同一数值路径、同一 dtype、同一缓存输入）的全部输出（去掉 hidden 与 MDN 的 std 半边），逐维按训练集上原输出的标准差归一化后 MSE；
  只在宽走廊内没有行人 / 骑车人的帧上加（有行人的帧允许 plan 变）。
- 损失：L = BCE(主, 正例加权) + BCE(宽) + 0.1 · SmoothL1(距离 / 10) + λ_d · L_distill，两个辅助头各算一份。
- 优化：AdamW，stage 4 lr 3e-5、辅助头 1e-3，wd 0.01，batch 64，cosine，bf16 autocast。
- 两个预登记配置：λ_d ∈ {1, 10}。用 dev 50 个 scene 选：dev 上漂移中位 ≤ 0.10 m 的配置里 dev AUC 最高的那个；两个都不满足就选漂移小的。**val / WOD / P5 只报选中的那个**，另一个作描述。
- 训练量：两个配置合计 ≤ 2 GPU·h。

## 成功标准（跑之前写死）

**第 1 步（port）**
- P1 fp32 port 对 ORT CPU（3 stream × 300 step，全程用 port 自己的 recurrent state）：plan 位置（MDN 均值）max |Δ| ≤ 0.01 m；lead 均值 max |Δ| ≤ 0.05；lead_prob logit max |Δ| ≤ 0.01；
  `temporal` max |Δ| ≤ 1% × 其 p99 |值|；不累积：最后 50 step 的 max ≤ 2 × 最前 50 step 的 max（或两者都 ≤ 1e-4）。
- P2 训练分解对 stream（同 dtype）：plan 位置 max |Δ| ≤ 1e-3 m、`temporal` ≤ 1e-3 × p99。
- P3（描述，定训练 dtype）：bf16 / fp16 port 对 ORT 的差，与 ORT TensorRT fp16 对 ORT CPU 的差并列。无论数值多少，蒸馏的 teacher 与 student 走同一个数值路径，所以漂移只反映学习。
- port 不过 P1 或 P2 就停，报告。

**第 3 步（B 小试，全部在留出数据上）**

操作性选择（写于任何训练之前）：
- WOD 没有 GT 框，这是与 coordinator 原话「GT boxes」的偏离：检测点（地面接触点，rear-axle 坐标）外套 0.7 × 0.7 m 的脚印进走廊判定；
  抬升失败的行人 / 骑车人检测让该帧 `uncertain = True`（11.7% 的帧），训练时应当遮掉这些帧的行人损失。WOD 样本只取偶数帧号（YOLO 跑在 4 的倍数帧上为主，偶数占 82%）。
- navtrain 每个 token 的 9 个 context 位置按 NAVSIM 协议从 4 帧 2 Hz 历史里取（t = −1.6 为零 hidden，t − 0.2 早于 −1.5 s 的前一帧为零图），每个 log 内按图像对去重（平均 3.7 对 / token），
  缓存里存 `ctx`（token × 9 的 slot 下标）。
- **帧不预先落盘**：渲染（JPEG 解码 + 反投影）约 40 ms / 帧 / 核，36 万帧在 20 个 worker 上约 12 min，与 GPU 上的 trunk 前向同一量级；预渲染要 142 GB 磁盘（zlib 只压 1.4 倍），换不来 GPU 时间。
  所以 CPU 这一步实际只有标签（各约 1 分钟，16 核），宽到 70 核没有用处；渲染在 trunk 缓存时在线做。调度表上没有未被占的核（所有非 done 行覆盖了全部核），用的是本行 `op-train` 的 48–67。
