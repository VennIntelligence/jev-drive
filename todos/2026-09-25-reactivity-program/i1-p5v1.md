## 目标

v0 的考卷成立，但只有一个 expert（特权规则驾驶器，读仿真器真值、不看相机）：CARLA 自带的 BehaviorAgent。它刹车晚、不会在行人前提前减速，
于是两个行人 family（PedestrianCrossing 3 个 reactive 帧、VehicleTurningRoutePedestrian 10 个）没进合并，Light 只有 9 个 reactive 帧，
合并翻转率的 CI 也宽（TFv6 waypoint [28.5, 50.1]）。v1 做三件事：

1. 加第二个 expert **PDM-Lite**（carla_garage / SimLingo 作者的规则 expert，会用行人的匀速外推提前减速），两个 expert 在同一批 pair 上各开一遍、各出一套标签；BehaviorAgent 保持 v0 原样，v0 与 v1 可比。
2. base 路线从 55 条（任务书写的 25 是 v0 进合并的路线数）扩到 **101 条**，每条仍是 3 个 TM seed（Traffic Manager 的随机种子，决定背景车流），family 与 v0 相同的 10 个，null pair（只换天气、正确动作不变的对照）照 v0。
3. 让 PedestrianCrossing、VehicleTurningRoutePedestrian 和 Light 有足够的 reactive 帧 / pair 进合并数。

交付：两个 expert 的 pair 集与标签（v0 管线 `p5_pairs` 建的 pairs / 观测帧 / null 帧 / 帧索引），每个 expert 一张 label-validity 表，
以及两个 expert 在同一批 pair 上的 Δ 对比。

**与旧草稿的冲突**：[P5 v1 E 层草稿](../2026-09-24-p5-v1-e-layer.md)（2026-09-24，draft）范围更宽：把 Light 移出 E 层、加绕行类 family 和横向 Δ、加新考生。
本任务按 reactivity 计划的 I1 行执行：**Light 和两个行人 family 都留在合并集里，family 与 v0 相同，只有纵向 Δ**。草稿里其余内容不在 I1 范围。

### 世界、run 与复用

每个 case（base 路线 × seed）有 x⁺（因素在）和 x⁻（因素不在）两个世界，seed 0 另有一个 null 世界，所以每个 expert **707 个世界**（303 × 2 + 101）。
x⁺ / x⁻ / null 的构造、`_rng` 重置 hook、hazard actor 藏到地下 500 m、HardBreakRoute 把急刹换成空操作、Light 红绿互换，全部是 v0 的代码，一字未改；
`build` 对 v0 的输入重新生成的 `pairs.xml` 和 `cases.csv` 与 v0 盘上的逐字节相同（已核对）。

| expert | 树（leaderboard + scenario_runner） | 世界 | 复用 v0 | 新跑 |
|:--|:--|--:|--:|--:|
| BehaviorAgent(normal)（`ba`） | 官方 Bench2Drive 0.0.4（与 v0 相同） | 707 | 385（v0 的全部 run，逐个核对 variant XML 与 v0 相同后链接） | 322 |

### 第二个 expert：PDM-Lite

用 SimLingo 仓库自带的 Bench2Drive 副本里的 `leaderboard/team_code/autopilot.py`，原样运行（它在公开的 B2D 220 上 DS 97.0，infra 验收里 `b2d_expert_agent.py` 也是它）。
它需要那棵树在 `CarlaDataProvider.active_scenarios` 里的登记，所以 PDM-Lite 的 run 在 SimLingo 树里跑。这棵树与官方 0.0.4 的差别（[SimLingo catalogue](../2026-09-25-simlingo-catalogue/README.md) 的 D1–D7）
都不改 actor 行为：D1（4000 tick 上限）和 D2（完成阈值 90）在我们 ≤ 50 s 仿真、触发后 20 s 就截断的录制里碰不到或只影响路线结束的那一刻，D5 只记账。

接法：recorder（`p5_pair_agent.py`，本身是 TFv6 的 `SensorAgent`，挂 TFv6 自己的传感器做 shadow 推理）新增 `driver: pdm_lite`，第一个 tick 实例化一个内层 `AutoPilot`，
交给它与 BehaviorAgent 相同的稠密路线，每 tick 用同一份 `input_data` 调它的 `run_step`（它只读 IMU 的 compass，这个 id 与 TFv6 的 IMU 同名同规格，其余都直接查仿真器）。
Waymo 三相机、actor 快照、可见性、TFv6 shadow 都与 v0 一样记录，所以 owner 之后可以在 PDM-Lite 开出来的帧上考同一批考生。
三处必须处理、但不改 PDM-Lite 行为的细节：

| 细节 | 问题 | 处理 |
|:--|:--|:--|
| 转向噪声 | `control.steer += 1e-3 · np.random.randn()`，用的是进程全局的 numpy 随机流；两个世界各自一个进程、没播种，x⁺ 与 x⁻ 会从第一个 tick 起毫米级分叉，1 cm 的确定性门槛就被它触发 | 给 PDM-Lite 一条自己的随机流（每次调用前后换入 / 换出 `np.random` 的 state），以 TM seed 播种：同一 case 的 x⁺、x⁻、null 抽到同样的噪声，噪声本身保留 |
| `SAVE_PATH` | LEAD（TFv6）需要它；PDM-Lite 在 import 和 `setup` 里读到它就会开始写自己的数据集 | 只在 import / setup PDM-Lite 那一刻把它从环境里拿掉 |
| 藏起来的 hazard actor | x⁻ 把 hazard actor 放在地下 500 m；若 expert 用二维距离，就会对看不见的行人刹车 | 读代码确认：行人外推、他车 bbox 预测都先用三维距离过滤（`detection_radius` 50 m），`compute_leading_vehicles` 虽用二维距离，但只在三维过滤后的 bbox 集合上起作用；`active_scenarios` 只用于绕行类 scenario（不在我们的 10 个 family 里）。null 与 x⁺/x⁻ 在因素可见前的逐 tick 相同是经验上的检查 |

环境：PDM-Lite 的 run 用 `envs/p5v1-pdm`：一个 Python 3.10 venv，底下挂 SimLingo 的环境（`envs/simlingo`，numpy 1.23.5、torch 2.8 cu128，infra 验收里 PDM-Lite 就在这个环境里跑），
自己只装 LEAD（TFv6）import 需要而 SimLingo 环境没有的包（`--no-deps`，版本照 `envs/scout-tfv6`，numba 换成支持 numpy 1.23 的 0.60），不改动任何共享环境。
BehaviorAgent 的 run 仍用 v0 的 `envs/scout-tfv6`。（预登记时写的是「都用 `envs/scout-tfv6`、补装 `rdp`」，集成 smoke 发现 PDM-Lite 在 numpy 1.26 下崩溃后改的，见偏离记录第 1 条。）

### 标签与判据（全部沿用 v0，每个 expert 各算一遍）

- 观测帧、v2（2 s 处速度）、Δ_expert = v2(x⁺) − v2(x⁻)、reactive = |Δ_expert| > τ_exp，τ_exp = max(该 expert 的 null p95, 0.5 m/s)：v0 原文。
- label-validity 表的列与 v0 相同（`p5_exam.exam` 不带考生调用）：pair、通过确定性检查（t_div ≥ t_vis）、丢弃原因、观测帧、reactive 帧、含 reactive 的 pair、Δ 中位数、纯度、进不进合并。
- **进合并**：该 family 至少 5 个 pair 含 reactive 帧（v0 规则，按 expert 分别判）。
- **判据**（v0 原文，按 expert 分别判）：通过确定性检查的 pair < 50% → 先修生成器；合并 reactive 帧 < 100 或占合并 family 观测帧 < 20% → 标签太稀。
- **I1 的目标是否达到**（写于任何数字之前）：PedestrianCrossing、VehicleTurningRoutePedestrian、Light 三个 family 在**至少一个 expert** 下按 v0 规则进合并，算达到；
  另报每个 family 的 reactive 帧数，≥ 30 帧的 family 才说它的翻转率「有得读」（30 是本文件定的描述性门槛，不是 v0 判据）。
  「两个行人 family」指的是 v0 里没进合并的 PedestrianCrossing 和 VehicleTurningRoutePedestrian；reactivity 计划里写的「45 + 76」是 DynamicObjectCrossing 和 ParkingCrossingPedestrian 的 reactive 帧（v0 已进合并），两处说法不一致，以没进合并的两个为目标，四个行人类都报。

### 两个 expert 在同一批 pair 上的对比（预登记）

两个 expert 开出来的 ego 轨迹不同，观测帧也就不同，所以对比按 pair 做，不按帧配对。只取两个 expert 下都通过确定性检查的 pair，按 family 报：
含 reactive 帧的 pair 数（BA / PDM / 两者 / 只有一方）、reactive 帧数、**反应提前量**（第一个 reactive 观测帧减 t_vis，秒）的中位数、reactive 帧上 Δ 的中位数、每 pair 最小 Δ 的中位数。

读法：PDM-Lite 在两个行人 family 上含 reactive 的 pair 明显多于 BehaviorAgent、提前量更小 → v0 的「行人没题」是 expert 造成的，v1 的行人题来自 PDM-Lite；
两个 expert 都 < 5 → 这两个 scenario 的行人在前视画面里出现时，任何一个规则 expert 都还不需要反应（scenario 设计问题），不是 expert 的问题；
两个 expert 在 cut-in family 上一致（含 reactive 的 pair 数相近）是 sanity check。

## 布局与启动

原计划是 21:30 之后、等 infra agent 的 CARLA profiling 结束、再等 owner 确认 layout 最多 30 min 才启动（夜间，GPU 1、2）。
**16:20 CST main 改了排程**（见偏离记录第 2 条）：infra agent 在 gpu-plan.md 写出 `[INFRA-PROFILE] layout ready` 就启动（目标约 18:00），
用它报的 layout，先在 GPU 4 上跑，GPU 2 等 I3 的渲染结束后再加上；不再等 owner 确认。现在挂的是：

| slot | 门 | 做什么 |
|:--|:--|:--|
| `p5v1-wait-infra` | 无 | `scripts/p5v1_wait_infra.sh`：每分钟看一次 gpu-plan.md，出现含 `[INFRA-PROFILE] layout ready` 的行就退出；行里若有 `servers_per_gpu=N`、`cores_per_server=C`，写进 `runs/p5v1/layout.infra.env` |
| `p5v1-gen` | `--after p5v1-wait-infra` | `scripts/p5v1_gen.sh`：读 `runs/p5v1/layout.env`（我们的默认值，见 profiling 一节），再读 `layout.infra.env` 覆盖每卡实例数和每实例核数；每张卡一条链 |
| `p5v1-index` | `--after p5v1-gen` | `scripts/p5v1_index.sh`：两个 expert 各跑一遍 v0 管线（`processed/carla_p5v1_{ba,pdm}`），再出 validity 与对比表（`research/results/p5-v1/`） |

链的细节：GPU 4 的链立刻开始；GPU 2 的链（`GATE_2=i3`）先等 I3 在这张卡上的渲染结束：`layout.env` 里写了 `I3_FINAL_SLOT` 就等那个 sentinel，
否则等「至少一个 `i3-*.done`、没有任何 `jev:i3-*` 窗口还有活的子进程、卡上空闲 ≥ 40 GB」连续 3 次（间隔 5 min）成立。
每条链从自己的 CPU 列表（GPU 4：52–103，GPU 2：156–189，都在这两张卡的 NUMA node 1 上）里取「实例数 × 每实例核数」个核，
先剔除启动那一刻任何活进程被 pin 到的核，所以不会和别的任务或另一条链重叠。每条链按 pass（2 遍）× expert（先 PDM-Lite 再 BehaviorAgent）
跑该 expert 还没完成的世界；所有链共用每个 expert 一个 `--out`（claim 分路线），第 j 条链占 server index 800 + 50j 起的 50 个（`b2d_run --index-span`，挪 server 时在块内回绕）。
PDM-Lite 用 SimLingo 的树与 `envs/p5v1-pdm`，BehaviorAgent 用官方树与 v0 的 `envs/scout-tfv6`。用了哪个 layout 复制成 `layout.used-<时间>.env`，每条链的开始 / 结束写进 gpu-plan.md（`[REACTIVITY/I1]`）。
每个 expert 完成 ≥ 95% 的世界就以 0 退出，index slot 在已有的世界上建。

续跑：被杀后重新挂同样的三个 slot（`p5v1-wait-infra` 会因为那一行已经在 gpu-plan.md 里而立即通过），已完成的世界跳过，死掉的 runner 的 claim 按 pid 立刻被接管，
上一轮留下的 CARLA server 由启动时的 reap 清掉。
