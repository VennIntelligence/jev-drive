# Probe v0：先立 baseline，再在 nuScenes mini 上打通 feature → probe pipeline

状态: done（v0 在 mini 上跑通；结论见「结果」，v1 换 trainval）
主题: ../research/qwen-latent-driving.md

## 目标

v0 不回答科研问题，只做两件事：

1. **先把 baseline 和标签立住。** 不看 Qwen，先回答"这个任务光靠 ego 运动状态能做到多少分"。
2. **把 pipeline 端到端跑通。** nuScenes mini → label → Qwen3-VL-4B 多层 feature → linear probe → 指标表。
   跑完以后，换 trainval 只需要改数据路径。

## 为什么这样设计

- **Ego-state baseline 是整个故事的前提。** 未来 2s 转不转弯，很大程度上由当前速度、yaw rate 决定。
  Qwen latent 必须**超过**"只看过去轨迹"的 baseline，才能说明它从画面里读出了东西。
  所以 baseline 放在 Qwen 之前做：如果 ego-state 已经接近满分，说明标签太容易，要先改任务定义。
- **要区分"Qwen 特有"和"任何视觉 feature 都行"。** 加一个小视觉 backbone（DINOv2）作对照。
- **mini 只能 debug。** CAM_FRONT 只有 404 个 keyframe，val 只有 2 个 scene、不到 100 个样本。
  v0 的数字一律不当结论。有统计意义的实验在 v1 用 nuScenes trainval 做。
- **v0 只做单帧。** z 怎么取（vision mean-pool / last token / 带不带 prompt）本身就是变量，
  先在单帧上把它定下来，再上 temporal。

### 实现

代码在 `jevdrive/`：`nuscenes_index.py`（直接读 JSON 表建 keyframe 表和每个 scene 20 Hz 的 ego 轨迹，
不用 devkit 的 `NuScenes` 类，因为它在 trainval 上要加载全部 annotation，很慢）、`labels.py`、`features.py`、
`probe.py`，入口是 `probe_v0.py`。feature 存在 `$DATA_DIR/processed/nuscenes/<version>/features/<backbone>/`，
每个 (layer, pooling) 一个 `(n, d)` 的 float16 `.npy`，加一个 `index.parquet` 记录行对应的 sample token。

几个实现上的选择：

- **标签**：用 LIDAR_TOP 的 20 Hz ego pose 做线性插值，yaw 先在 scene 内 unwrap（消除 ±180° 跳变）再插值。
  未来 2 s 的 Δyaw > +5° 为 left，< −5° 为 right，其余 straight。
- **ego-state 特征**：过去 2 s 每 0.5 s 采一个 pose，得到 4 段速度、4 段 yaw rate、3 个加速度，共 11 维。
- **Qwen 输入**：chat template 里只放一张图，不带文字 prompt，加 assistant 的 generation prompt，
  所以 last token 就是模型开始作答的位置。原始分辨率 1600×900 → 1400 个 visual token，序列长 1410。
- **Qwen feature**：`vit_mean`（patch merger 之前的 ViT 输出，1024 维）、`vis_mean`（merger 之后、LLM 看到的
  visual token，2560 维），以及 LLM 第 9/18/27/36 层（共 36 层）残差流的 image-token mean 和 last token。
  用 forward hook 在 GPU 上直接 pool，不保存完整 hidden states。
- **DINOv2**：ViT-B/14，整帧 resize 到 252×448（不做 center crop，否则会裁掉左右两侧），取 CLS 和 patch mean。
- **Probe**：linear probe（冻结 backbone，只训一个线性分类器，用来测 feature 里有没有线性可读的信息）用的是
  standardize + multinomial logistic regression，正则强度 C 在训练 scene 内做 scene-grouped inner CV、按 NLL 选。
  "+ego" 是把 Qwen feature 和 11 维 ego-state 直接拼接。
- **额外加的 baseline `ego_rule`**：不训练，直接把当前 yaw rate 外推 2 s 再套同样的 ±5° 阈值。
  它用来衡量"标签有多容易"。它输出的是平滑过的 one-hot（ε=0.05），所以它的 NLL/Brier 只反映 ε，不能和其他行直接比。

### 检查点结论

ego-state 本身**已经能解释大部分转弯，但学习型的 ego probe 在 mini 上学不出来**：

- 不训练的 `ego_rule` 在 LOSO（leave-one-scene-out，每次留一个 scene 做测试，10 折预测拼起来，n=314）上
  acc 0.914、macro-F1 0.817、turn recall 0.764。55 个转弯样本里有 45 个在当前时刻已经有 ≥1°/s 的 yaw rate。
  也就是说，这个标签大部分是"正在转的车会继续转"，确实偏容易。
- 学习型 `ego` probe 反而只有 macro-F1 0.424，因为训练样本太少、类别极不平衡，inner CV 选出很强的正则（C≈0.03），
  预测几乎全是 straight。单独试过：固定 C=1 能到 acc 0.873，再加 `class_weight="balanced"` 能到 macro-F1 0.741。
- 按计划真正该看的是 hard subset（当前 yaw rate ≈ 0、但未来要转）。mini 上只有 10 个这样的样本（val 上 3 个），
  在 mini 上没法评估。**决定：标签定义不变，v1 的主指标改成 hard subset 上的指标，全量指标作为辅助。**
  按 mini 的比例（10/314）估算，trainval 大约有 ~800 个 hard 转弯样本，够用。

### 遇到的问题

- box 上 uv 从 GitHub 下 Python 3.11 会卡住（直连和 turbo 都一样），改用 npmmirror 的 python-build-standalone 镜像，已写进 `docs/python-env.md`。

- nuscenes-devkit 1.1.x 会把 matplotlib 锁到 3.5（不兼容 numpy 2），所以用 1.2.0，并且只用它的 `create_splits_scenes`。

### 给 v1（trainval）的建议

1. **主指标看 hard subset**（当前 yaw rate ≈ 0，未来 2 s 转弯）。全量指标会被"正在转弯的车"主导，ego_rule 已经能拿到 0.9 的 acc。
   阈值 1°/s 可以在 trainval 上再扫一遍，看 hard 转弯样本数和 ego_rule 的表现。
2. **probe 要处理类别不平衡**：加 `class_weight="balanced"`，或者额外报和阈值无关的指标（每类 AUROC / AUPRC）。
   inner CV 用 NLL 选 C 在小数据上会选出很强的正则，trainval 上应该好很多，但仍然建议同时报 balanced 的版本。
3. **"+ego" 拼接要改**：2560 维图像 feature 和 11 维 ego 共用一个 C，ego 信号被淹没（+ego 行和 image-only 几乎一样）。
   建议先把图像 feature 用 PCA 降到 ~64 维再拼接，或者做 late fusion：ego probe 的 logit 作为 offset，只学图像部分的残差。
4. **加 scene-level bootstrap CI**（按 scene 重采样），不然层与层之间的差距没法判断是不是噪声。
5. **层数**：probe 本身很便宜，瓶颈是抽 feature。建议 trainval 上存全部 36 层的 last token 和 image mean（约 12.6 GB），
   一次就能画出完整的 layer 曲线，不用反复抽。
6. **分辨率**：800 px 快 4.6×（41 vs 187 ms/frame）。建议先在 trainval 的一个子集上比较 800 px 和原分辨率的 probe 结果，
   差距不大就全量用 800 px。
7. Qwen 深层 last token（L27/L36）在 NLL 和 balanced turn recall 上都是图像 feature 里最好的，v1 重点验证这一点，
   以及它是不是只比 ego 多出一点"路口/车道形状"的信息。

## 性能优化（v1 前）

2026-09-19。目标是让 v1（nuScenes trainval CAM_FRONT，34149 帧，带标签的 26491 个样本，850 个 scene）整条链路尽量快。
这次只在 trainval 的子集上做 benchmark，没有跑全量。代码在 commit `02dfc43`，benchmark 脚本和中间结果在 box 的 `$DATA_DIR/tmp/perf/`。

### 先说一个环境上的发现

box 的宿主机有 128 核、500 GB 内存，但我们容器的 cgroup（Linux 用来给进程组限额的机制）只给了
**16 核**（`cpu.max` = `1600000 100000`）和 **62 GB 内存**。`nproc` 和 `os.cpu_count()` 报的仍然是 128。
这带来两个后果：一是旧 probe 的 `joblib(n_jobs=-1)` 会起 128 个进程抢 16 个核；二是旧 `load_features` 会把全部 feature
转成 float32 读进内存，再把 "+ego" 版本 hstack 一份，trainval 上要 80 GB 以上，会直接 OOM。
所以旧代码在 trainval 上实际跑不完 probe 这一步。`docs/remote-box.md` 已更新，代码里改用 `common.n_cpus()` 读 cgroup 限额。

### 前后对比

feature 这部分，Qwen 在 trainval 前 2000 帧（800 px）和前 1000 帧（原分辨率）上测，DINOv2 跑的是全部 34149 帧。
batch 都是 8，DataLoader worker 16 个。ms/frame 是去掉第一个 batch 后的稳态值。CPU 是整个进程组平均占用的核数（按 cgroup 统计），
GPU util 是 nvidia-smi 的平均值。

| stage | 版本 | ms/frame | 外推 trainval 34149 帧 | peak VRAM (GB) | CPU（核） | GPU util |
|:--|:--|--:|--:|--:|--:|--:|
| Qwen 800 px（`qwen_w800`） | 旧 | 41.5 | 23.6 min | 8.89 | 2.5 | 86% |
| | 新 | **30.8** | **17.5 min** | 8.65 | 3.8 | 88% |
| Qwen 原分辨率（`qwen`） | 旧 | 199.9 | 1.90 h | 10.58 | 1.8 | 87% |
| | 新 | **142.4** | **1.35 h** | 9.62 | 2.8 | 85% |
| DINOv2 | 旧 = 新 | 1.6 | 1.0 min | 0.96 | 14.1 | 69% |

只看 GPU、不走 DataLoader 的 forward：原分辨率从 178–183 降到 139.5 ms/frame，800 px 从 39.3 降到 29.9 ms/frame。
按 FLOPs 估算（原分辨率每帧约 17.6 TFLOP，800 px 约 3.7 TFLOP），现在的有效算力约 125 TFLOPS。实测 bf16 matmul 的峰值约 142，
已经接近 roofline（硬件算力上限）。不做量化的话，feature 这一步剩下的空间不大。
DINOv2 的瓶颈在 CPU 解码，全量只要 1 分钟，没有动它。

probe 部分是 linear probe（冻结 backbone，只训一个线性分类器）。每个 feature set 要拟合 6 个 outer fold：官方 val 1 个，
加上按 scene 分组的 5-fold。每个 fold 内部又要做 4 折 inner CV × 13 个 C，再加上 refit。
旧版用 sklearn，每个 fit 占 1 个核；新版在 GPU 上一次解完 390 个问题。

| feature set | n | d | 旧：sklearn（core-s，6 个 fit 合计） | 新：GPU（s） |
|:--|--:|--:|--:|--:|
| dinov2/cls | 26491 | 768 | 551 | 1.9 |

| qwen_w800/L18_mean | 9272 | 2560 | 868 | 2.1 |
| qwen_w800/vis_mean | 9272 | 2560 | 1388 | 3.6 |

这里的 9272 是前 12000 帧里有标签的样本（303 个 scene）。

外推到 v1 的 probe 全量：共约 307 个 set，即 2 × 76 个 Qwen 数组、它们各自的 "+ego" 版本、2 个 DINOv2 数组和 ego。
sklearn 的单次 fit 时间大致和 n 成正比，n=26491 时 2560 维约 430–690 core-s。
在 16 核上，旧版只把 outer 改成 5-fold 也要 **14–22 h**；按原代码的 LOSO 跑，要 851 个 outer fold，是好几个月的量级，还没算 OOM。
新版在 n=9272 时每个 set 2–4 s。时间主要花在迭代次数和 kernel launch 上，n 增大后会慢一些。
按 3–8 s/set 估算，全量约 **15–40 min**。这个数是外推的，没有在全量 2560 维数据上实测。

### 改了什么

- `jevdrive/features.py`，Qwen 这一路：
  - 不再用 forward hook 和 `Qwen3VLModel.forward`，直接逐个调 vision block 和 decoder layer，在 loop 里做 pooling。
    模块和数学都不变，layer 1–3 的输出仍然取在 DeepStack 注入之前。
  - vision attention 改成一次 batched SDPA（PyTorch 的 fused attention，这里走 flash kernel）。
    原来的 sdpa 路径在 24 个 block 里每个都要按图片 `cu_seqlens.tolist()` 拆一次，每次都会让 host 等 GPU。
  - M-RoPE（多模态旋转位置编码）的 position ids、rotary 表和 image token 的位置，对每种 batch shape 只算一次。
    所有帧的尺寸和 prompt 都一样，结果也就一样。
  - 每个 block 和 layer 单独 `torch.compile`，把 norm、rotary、激活这些 elementwise op 融合起来。
    所有 layer 共用一个 graph，每种 batch shape 编译一次，约 10 s。
  - D2H（GPU 到 host 的拷贝）改成异步：76 个数组先拼成一个 fp16 tensor，non-blocking 拷进 pinned memory，
    再由一个 writer thread 写 memmap。GPU 不用再等 I/O。
- `jevdrive/probe.py`：
  - 用 GPU 上的 batched L-BFGS（限内存拟牛顿法）解 multinomial logistic regression，目标函数和 sklearn 完全一样：
    平均 CE + ‖W‖²/(2Cn)，intercept 不惩罚，停止条件 gtol=1e-4，max_iter=3000。
    StandardScaler 按 outer fold 折进权重里，数学上等价。选 C 同样按 inner CV 的 neg log-loss，平局取第一个。
  - 一个 feature set 的全部 390 个问题用 0/1 权重 mask 共享同一份 X，每一步只做两个大 GEMM。
    收敛的问题会从 batch 里移出去。
  - scene 数超过 50 时，outer 从 LOSO 改成按 scene 分组的 5-fold（`kfold`）；mini 上仍然是 LOSO，官方 val 保留。
  - feature 从 memmap 按 set 流式读到 GPU，后台线程预取下一个 set，不再整体读进内存。
  - "+ego" 现在也覆盖 `qwen_w800`。
- `jevdrive/probe_v0.py`：`--qwen-width` 接受逗号列表，比如 `800,native`，一次 run 出两个 set；
  新增 `--probe-sets <regex>`；worker 数和 torch 线程数默认取 cgroup 限额。

### 等价性检查

**feature**：同样的帧，新代码和旧代码逐数组比较。bf16（16 位浮点，只有 8 位有效尾数）本身就带噪声，
为了知道噪声有多大，另外拿**旧代码自己**的 bs=1 和 bs=8 比了一次，作为 noise floor。
max_rel 是最大绝对差除以该数组的最大绝对值，cos 是逐样本的余弦相似度。

| 比较 | 数组 | max_rel | 平均相对 L2 误差 | cos_min |
|:--|:--|--:|--:|--:|
| 新 vs 旧，800 px | vit_mean / vis_mean | 0.006 / 0.005 | 0.002 / 0.005 | 1.000 |
| | L01–L35 `_last` | ≤ 0.028 | ≤ 0.019 | ≥ 0.999 |
| | L01–L16、L35、L36 `_mean` | ≤ 0.066 | ≤ 0.024 | ≥ 0.999 |
| | L17–L34 `_mean` | 0.10–0.23 | 0.015–0.039 | 0.970 |
| | L36_last | 0.128 | 0.029 | 0.998 |
| 旧 bs1 vs 旧 bs8，800 px（noise floor） | L17–L34 `_mean` | 0.30 | 0.041 | 0.950 |
| | L36_last | 0.161 | 0.032 | 0.999 |
| 新 vs 旧，原分辨率 | 全部 76 个 | ≤ 0.134 | ≤ 0.027 | ≥ 0.997 |

结论：新旧之间的差异**不超过**旧代码换一个 batch size 带来的差异，属于 bf16 噪声。
L17–L34 `_mean` 偏大，是因为 channel 4 是一个 massive activation（个别 token 上数值特别大的 channel），在 image-token 平均里约为 60–90。
这个 channel 对 bf16 的累加顺序很敏感，旧代码自己的抖动也有 ±2 左右。
这对 probe 可能有影响：做 standardize 之后，这个 channel 的噪声会被放大。v1 分析 mean pooling 时要记得这一点。

**probe**：trainval 上直接和 sklearn 逐 fold 比较。val 和 kfold 两个 protocol 的指标：

| set | n | max \|Δp\| | val NLL 旧 / 新 | kfold NLL 旧 / 新 | kfold acc 旧 / 新 |
|:--|--:|--:|--:|--:|--:|
| ego | 26491 | 0.067 | 0.3390 / 0.3390 | 0.3103 / 0.3103 | 0.8997 / 0.8997 |
| dinov2/cls | 26491 | 0.004 | 0.4411 / 0.4411 | 0.4587 / 0.4586 | 0.8355 / 0.8357 |
| qwen_w800/L36_last | 9272 | 0.003 | 0.4939 / 0.4940 | 0.5473 / 0.5473 | 0.7966 / 0.7965 |
| qwen_w800/L18_mean | 9272 | 0.004 | 0.4747 / 0.4748 | 0.4870 / 0.4871 | 0.8242 / 0.8241 |
| qwen_w800/vis_mean | 9272 | 0.002 | 0.5401 / 0.5401 | 0.5679 / 0.5679 | 0.7949 / 0.7951 |
| qwen_w800/L36_last+ego | 9272 | 0.007 | 0.4082 / 0.4086 | 0.4296 / 0.4297 | 0.8428 / 0.8429 |

NLL 的差在 5e-4 以内，acc 的差在 6e-4 以内，和 sklearn 等价。
ego 的 max |Δp| 偏大，是因为有一个 fold 的 inner CV 在 C=31.6 和 C=100 之间几乎打平，两边选了不同的 C，但 NLL 完全一样。
C 相同时，refit 出来的概率差在 5e-5，objective 差在 1e-8。

**mini 上和 v0 对照**：官方 val 这张表基本复现了 v0，比如 ego 1.684、dinov2/cls 1.455、qwen/L18_mean 1.172 都完全一致。
qwen 各层差在 0.01 以内，因为 mini 的 qwen feature 这次用新代码重抽了。
但 mini 上的 **LOSO 数字和 v0 不一样**，比如 qwen/L36_last 的 NLL 是 0.640，v0 是 0.552。
原因是 mini 的 inner fold 里经常整类缺失，比如官方 val 的第一个 inner fold 训练集里一个 right 都没有。
缺失那一类的 intercept 没有惩罚，会一直往 −∞ 走，停在哪里取决于优化器什么时候停。这类 fold 的 held-out log-loss 因此没有良定义，
sklearn 和 GPU 版各停在不同的位置。trainval 上每个 inner fold 都有上百个转弯样本，不会出现这种情况，上表也证明两者一致。
这件事再次说明，mini 上的 probe 数字不能当结论。

### 试过但没有收益的

- **加大 batch**：原分辨率 bs 1/4/8 分别是 147.7/139.8/139.5 ms，800 px 的 bs 4/8/16/32 是 31.5/29.9/30.2/30.2 ms。
  v0 说"原分辨率已经 compute-bound"是对的，默认值保持 8。
- **probe 沿 C 的路径 warm start**（sklearn 的做法）：总迭代量降到 1/2–1/3，但 13 个 C 只能串行解，
  kernel launch 的开销反而更大，vis_mean 从 3.6 s 变成 8.3 s，所以撤回了。
  把 line search 的最大回退次数从 30 降到 10：速度基本不变，留着。
- **没做的**：GPU 上做 JPEG 解码和预处理（CPU 只用了 16 核里的 3–4 核，不是瓶颈）；flash-attn（SDPA 已经在用 flash kernel，
  瓶颈在 matmul，不值得多一个依赖）；DINOv2 和 Qwen 并发（DINOv2 只要 1 分钟，而且吃 CPU）；
  probe 的 preconditioned L-BFGS（按每个 fold 的协方差做预条件，可能再把 probe 快几倍，但代码更复杂，probe 已经不是瓶颈了）。

### 风险和没验证的地方

- probe 全量的耗时（15–40 min）是从 n=9272 外推的，没有在全量 2560 维数据上实测。
- 新的 Qwen forward 直接调了 transformers 5.17 的几个内部 helper（`transformers.vision_utils`、`compute_3d_position_ids`）。
  版本锁在 `uv.lock` 里；升级 transformers 后要重新做一遍等价性检查。
- `torch.compile` 第一个 batch 要编译约 10 s，最后一个不满的 batch 会再编译一次，约 3 s。
  同一个进程里连续跑两种宽度已经验证过，第二个模型没有退回 eager。
- 在 mini 上跑整条 CLI 已通过（run `20260919-214434`）：features 88 s；probe 173 个 set × 715 个问题，216 s，没有不收敛的警告。

### v1 启动命令

在 box 上执行：

```
cd ~/data/jev-drive && scripts/tmux_run.sh probe-v1 scripts/probe_v0.sh --version v1.0-trainval --qwen-layers 36 --qwen-width 800,native
```

这条命令会依次跑 index、labels、features（DINOv2 → `qwen_w800` → `qwen`）和 probe（全部 set，val + kfold）。
预计 features 约 1.7 h，probe 约 15–40 min，合计 **约 2–2.4 h**。feature 占盘约 2 × 12.5 GB，现在剩余 317 GB。
如果想先看 800 px 的结果，可以先只跑 `--qwen-width 800`，约 20 min + probe；之后再补 native，已有的 set 会被跳过。
