# 17. 闭环评测是小时级，不是天级——但便宜是「接得对」换来的，不是卡换来的

**事实**（2026-09-21 实测，未修改的 Bench2Drive 0.0.4 leaderboard 跑真实路线，
完整数据见 [docs/bench2drive-cost.md](../../docs/bench2drive-cost.md)）：

44 条 base-package 路线、4 个 worker、Qwen3-VL-4B 真的在环里，**0.71 小时**跑完。
外推 220 条：优化后 8 实例 **约 1.1 小时**〔2026-09-22 全量实测为 3.11 小时，见下面的就地修正〕，按 Bench2Drive 原样接则 **约 15 小时**，
同路线同卡差 **13.9×**。**结论：闭环评测是小时级，不需要换机器。**

**时间花在哪**：3 相机 1600×900 的一个 tick 是 158 ms，其中 **128 ms 是阻塞等相机帧**（79%），
scenario tree 25 ms，`world.tick()` 只有 8 ms。

**三条反直觉的、会改变做法的结论**：

1. **相机成本是 per-sensor 不是 per-pixel。** 像素砍到 1/16 只快 3%（在噪声带内），
   每多一个相机固定加 33 ms/tick。降分辨率没用，**减帧数（decimate）才有用**：2/4/10 → 1.76×/2.12×/3.36×。
   前提是先修一个 leaderboard 的 bug：`_preprocess_sensor_spec` 的白名单里没有 `sensor_tick`，
   agent 要 5 Hz 会被静默地给 20 Hz，所以 decimate 在修之前**一点用都没有**。
2. **按模型输入尺寸直接渲染是单笔最大收益，而且免费。** 仿真侧不要钱（与分辨率无关），
   policy 侧省掉 resize：Qwen 三相机 139 → 59.9 ms，DINOv2 21.9 → 5.3 ms。
   连带纠正：我们 [waymo-e2e.md](../../docs/waymo-e2e.md) 的 127–216 ms/frame 是离线吞吐，
   **闭环里预处理占延迟的 70%**。论文里要写清 800×450 直出 ≠ 1600×900 降采样。
3. **不要写 Cython。** 热点是唯一一个函数（`RouteLightsBehavior._turn_close_lights_on`，占总时间 14.5%），
   而它花时间在「为不变的数据反复发 RPC」。语义等价地缓存掉之后 scenario tree 快 3.2×，
   **wall clock 一点没变好**——leaderboard 的 Python 本来就藏在 sensor 管线后面。**单实例下 H4 天花板是 0。**

**并发上限是配置的属性，不是机器的属性**：第 16 条之后记的「4 实例封顶、第 6 个 segfault」
是在饱和负载（1 相机每 tick 1600×900）下测的。换成优化配置，**6 个和 8 个实例都跑得干干净净**，
总吞吐 1.37×/1.62×，8 个时 CPU 才到顶（23.8/25 核），显存 59/96 GB。

**稳定性**：3.5 个 worker 小时里 **CARLA 本身一次都没崩**。12 次重启全部是我们自己的
traffic-manager 端口复用（TM 的 RPC server 在客户端进程里）。
**没有排除的事**：Town12 的 sensor-dormancy segfault 够不着（base package 只有
Town01–05 和 Town10HD，**Town06/07 也不在里面**，220 条里只有 44 条能跑）；
「长时间无人值守第三小时卡死」也没有被 3.5 小时排除。

**状态**：成本结论已确认，并在 2026-09-22 被全量实测**修正了一次**（见下）；
**闭环要做**（原写「要不要做闭环仍未决定」；第 21 条 2026-09-22 已定）。

## 2026-09-22 就地修正：全量跑完了，「约 1.1 小时」是错的，实测 3.11 小时

上面那个「优化后 8 实例约 1.1 小时」是从 44 条 base-package 路线外推的，**乐观了 2.8 倍**，
而且错在它自己标注过的那一条假设上：**它假设大地图和小地图一样贵。**
AdditionalMaps 装好之后，全部 220 条、8 个 worker、同一套优化配置逐字复现，一条命令无人值守：
**11196 s = 3.11 小时**（01:17→04:24），209/220 条完成，245 次 attempt，633881 个 tick，exit 0。
完整数据见 [docs/bench2drive-cost.md](../../docs/bench2drive-cost.md)。

**「Large Map」不是那个预测变量，Town12 和 Town13 才是。** 上面那句
「Town12/13 是 151 条，按贵一倍算 3–4 小时」猜对了总时长，但把原因归错了地方：

| 地图 | 路线数 | ms/tick | 相对小地图 |
|:--|--:|--:|--:|
| 小地图 Town01–10HD（同一轮重测） | 55 | 64.3 | 1.00× |
| **Town11 + Town15**（一样是 Large Map） | 14 | **60.4** | **0.94×** |
| Town12 | 104 | 106.2 | 1.65× |
| Town13 | 47 | **156.8** | **2.44×** |

Town11 和 Town15 一样流式加载 tile，却和小地图一样便宜。**Town12 + Town13 占 69% 的路线、
83% 的 wall clock**。以后写这两张图的名字，不要写「Large Map」。

**第 16 条里「长时间稳定性完全没测」和「Town12 的 segfault 够不着」这两条，现在有答案了，
而且是坏消息**：11 条路线跑不完，**全部在 Town12/Town13**，每条三次 attempt、每次都在全新 server
的新端口段上、每次都在成功跑了 150–360 s 之后 `Signal=11` 崩掉，日志里没有 bind error。
36 次失败 attempt 全部是 `server_died_rc139`。Town11、Town15 和八个小地图一条都没失败。
**这是 sensor-dormancy segfault（Bench2Drive #235 / carla #7772）第一次在未经修改的官方
leaderboard 路径上复现出来。**
**推论：这台机器上的 Bench2Drive 分数最多是 209/220 条上的分数，而哪 209 条由 CARLA 决定。
任何报出来的分数必须带上这一条。**

**另外两条老结论被同一轮推翻**：(1)「这张 96 GB 卡对闭环过剩」只对小地图成立——
Town12 上每个 server 占 6.3 GB，10 个实例就是 83.5 GB（峰 87.4），12 个装不下，**显存是那个约束**；
(2)「第 6 个 server 在饱和负载下 segfault」很可能是**端口复用**：后来梯子里的两次启动 segfault
日志里都写着 `bind: Address already in use` 紧接 `Signal 11`——**CARLA 端口被占不报错，直接崩。**

**这 3.11 小时里有很大一块不是仿真器的：** 209 条完成的路线里 **56%（118 条）撞满了 4000 tick 上限**，
中位数正好是 4000，而路线本身平均只有约 100 m（6 m/s 开完约 330 tick）。
我们的 stand-in 故意开得烂、卡住之后一路跑到上限。**换一个真能开完路线的 policy，
这一轮会比任何一项工程优化省下更多时间。** 3.11 小时该读成「一个烂司机的上界」，不是仿真器的地板。
