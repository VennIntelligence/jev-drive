1. **三个开关（默认全关，关时 plan 与原来逐位相同）。** (a) `JEV_VCONT=1.0`：path 不变，速度剖面从 ego 当前速度起步、1.0 s 内线性并入 plan 自己的分段速度；1.0 s 来自控制器（AlpaSim 的 nonlinear MPC 只对 horizon 第 10–20 步即 1.0–2.0 s 的参考位置计 cost）。(b) `JEV_LEAD=1`：openpilot 自己的 lead 通路（ec95db3f 的 radard 概率滤波与 vision lead、`long_mpc.py` 的 cost / horizon / 限幅、planner 的取最小），用 checkpoint 同一次前向的 lead 输出，20 Hz tick，SLSQP 求解；速度剖面取与 lead MPC 速度解的逐点最小，只减速、无 latch。(c) `JEV_BASE=1|2`：adapter 的 path 配底模（关掉 adapter bias 的同一 policy）速度剖面；2 = 行进用底模、静止保留 adapter 起步，除非 lead 输出报告跟车距离内有车。与第 140、157、167、179、203 条及 `op_control_stack_long` 的区别写在预登记里：那些是固定余量 / resume 规则 / 关 bias / 离线 AUC，都没有把 openpilot 的跟车律放进闭环。
2. **nuPlan（700 public scene，P2H10-F-s0，与同 checkout 重跑的 base 0.9468 配对，log 整簇 CI）。** +a −0.0066 [−0.0272, +0.0112]，slow 112 → 68 但零分 26 → 32（新增 11 个：4 offroad / 4 corridor / 3 碰撞）；+b −0.0858，两个 lead-stopped 碰撞都变成 1.0，但 304 个 scene 被限速、平均 −0.199（openpilot 的 6 m + 1.45 s 跟车距离比日志司机长，分数是相对日志的 progress）；+a+b −0.0712；+c1 −0.1321，+c2 −0.0973，+c1+b −0.1521，+c2+b −0.1199，事后的 +c1+a −0.1064、+c2+a −0.0764。登记线无一通过，按停止规则没跑其余 791 scene 和 APY10m10-AB。OT3 的旧 run 与重跑 base 只差 1 个 scene（+0.0016），差值不是仿真噪声。(c) 不含 (a)：闭环记录里底模首段速度在 0.5–10 m/s 是 ego 的 0.84–0.96 倍。
3. **PAI（GPU box 原生 stack，PAI2 的 60 scene 与分块，P2H10-F-s0 / -s1，84 个 stack，按 scene 重采样的 CI）。** base 0.215（两 seed 0.173 / 0.257）；+a +0.058 [−0.015, +0.136]；+b +0.086 [+0.008, +0.172]；+a+b +0.148 [+0.061, +0.244]（0.359 / 0.366，at-fault 碰撞零分 14 / 11 → 5 / 3）；+c1 +0.095、+c2 +0.115（CI 含 0）；+c1+b +0.123 [+0.023, +0.228]；+c2+b +0.153 [+0.041, +0.273]。按登记读法 +b、+a+b、+c1+b、+c2+b 为 helps，最大的是 +c2+b，领先 +a+b 0.006，即打平；没有任何设计选择碰过的 40 scene 上两者 +0.1436 / +0.1440。(c) 的零分更少、slow 约多一倍（c1 有 28% 的决策处于静止），多一次 policy 前向（`drive` 中位 63 对 46 ms）。新增的 20 个 extension scene 上增益小（+a+b +0.038，+c2+b +0.075，CI 约 ±0.15）。Tokyo box 上 40 scene 单 seed：base 0.169，+a 0.292，+b 0.383，+a+b 0.462，(c) 各臂 0.32–0.39；box 的 parity run 与 Tokyo 8 / 10 个 scene 类别相同。
4. **护栏。** 从 main build 的镜像原本过不了 `test.sh`（driver 默认 `SH30_COMPILE=1` 在镜像里无法编译：先是只读根目录，再是没有 C compiler），Dockerfile 现在默认 `SH30_COMPILE=0`；之后 switches off 与 `VCONT=1.0 LEAD=1` 两个镜像都通过，`drive` p50 / p99 50.6 / 71.9 与 62.2 / 80.8 ms。box 跑 compiled、镜像跑 interpreted，是两条数值路径。(b) 在 nuPlan 节奏下每次调用多 12–16 ms，PAI 上多 2–4 ms。开关只在 AlpaSim driver 的导出步骤里，HUGSIM / jevdrive.bench 不经过。

**对方向的含义**：(1) 比赛：两个 track 要不同的 serving。nuPlan 镜像不动；PAI 用 `JEV_VCONT=1.0 JEV_LEAD=1`（或 `JEV_BASE=2 JEV_LEAD=1`），但 PAI 还没有提交镜像的 build 路径（closure、`serve.py` 的 pai 家族、PAI 形态的 probe 三处要补）。(2) 第 218 条的读法在闭环里成立一半：PAI 上 adapter 缺的「lead 触发的起刹」由 (b) 补上是主要增益来源，(a) 单独不过线；nuPlan 上同一个 adapter 先验正是分数，换成底模速度或 openpilot 跟车距离都按 progress 掉分。「同一 driver 两个 track」在 serving 层做不到，要靠训练（第 221 条已试过五个臂）。(3) nuPlan 上 (a) 暴露的一点：base 每个决策都被首段速度偏低 1–2% 轻微拖慢，去掉后 slow 少 44 个而横向零分多 6 个，速度与横向失败在这个 driver 上是耦合的。
