2026-10-09。lane alpasim-tokyo（image agent）。结果 [experiments/alpasim/results/tokyo_image_smoke.md](../../experiments/alpasim/results/tokyo_image_smoke.md)（小文件在 `results/tokyo_image/`），做法和用户的提交命令 [docs/alpasim.md](../../docs/alpasim.md)「Submission image」，代码 `experiments/alpasim/docker/`（`Dockerfile`、`build.sh`、`test.sh`、`smoke.sh`、`new_tag.sh`、`wheels.py`、`replay.py`）。执行者完成并写本条，main 没有复算。没有 push 镜像、没有登录 challenge CLI、没有提交，配额未动。

1. **提交路径（读源码，0bb4c4b；warm-up 读 HEAD 2023534）**：镜像只靠自己的 `CMD` 启动，拿到 `ALPASIM_DRIVER_HOST / PORT` 和 replica 两个环境变量，没有 healthcheck，runtime 用 `get_version` 等最多 240 s 并要求所有 replica 的版本一致；镜像推到 ECR `696254625193.dkr.ecr.us-east-1.amazonaws.com/teams/<team_id>:<tag>`（`latest` 被拒，tag 会出现在公开 leaderboard API 里）；warm-up track 只在 7611632 之后的 CLI 里；`--controller-gains` 是 7 个字段的 JSON 子集；官方 service 镜像不是拉取的，是 wizard 的 compose 用根目录 `Dockerfile` 本地 build 的 `alpasim-base:0.89.0`（无 lock，版本随 build 日期浮动；本次 19.7 GB，torch 2.8.0）。
2. **镜像**：`python:3.11-slim` + box 上 serving 环境的同版本包（uv，`requirements.lock` 带 hash；torch 2.14.0 取 `+cu126`，box 是 `+cu130`）+ 官方 `src/grpc` + `cinque.ort.onnx` + 18 个 repo 文件 + 每个 tag 一个 `ckpt-final.pt`；层按稳定程度排序，新 checkpoint 只多一层薄层；`JEV_TAG` 运行时选 checkpoint，driver 家族（`sh30` / `ap2` / `ens`）由 checkpoint 自己的记录决定，OT3 的 tag 不用改 Dockerfile。
3. **限制测试**（主办方本地脚本的全部 flag 加 `--network none`，2 个并发合成 rollout）：两个 driver 路径都过；镜像 7.48 GiB（上限 40），卡上峰值 3.04 GiB（上限 16），`/tmp` 0.21 MiB（48 scene 后 0.80 MiB，上限 2 GiB），`/run` 0，冷启动 19.4 / 19.8 s，`drive` p50 / p90 / max 86 / 97 / 124 ms（3090，不是主办方的卡，也不是 box 的 6000D）。
4. **官方容器化 stack 里的 48 scene**：P2H10-F-s0 0.9839、零分 0、满分 37（native 取自 OT3 的 700-scene chunk：0.9840 / 0 / 37，11 个 scene 差 ≤ 0.0062）；AP2-AB-s0 0.9521、零分 2（native 同一 48-scene 列表 0.9320、零分 3；43 个 scene 相同，4 个差 ≤ 0.0061，1 个 native 的 at-fault 碰撞在容器里是 0.9719）。容器化 stack 自己重复运行逐 scene 相同。
5. **为什么不逐位相同**：同一 scene 决策 0 的 CAM_F0 JPEG 两边字节相同（4 / 4），renderer 不是来源；同一张 JPEG 在镜像里打包成 model frame 有 89–162 / 393 216 个值不同（采样 map 在另一种 CPU 上舍入不同）；同样的 frame 和 ego 特征过模型，plan 差到 1 个 fp16 步长，导出位姿差中位 0.8 cm、最大 2.4 cm；到决策 9 两边 plan 已差 0.16–0.51 m。d211 的机制（厘米级差异被闭环放大）足以翻转一个临界碰撞。
6. **路上发现的两件事**：镜像里每个 gRPC worker 线程的首次推理多 1.35 s（native 日志里没有），driver 现在在开端口前让每个线程先跑一次推理（唯一的 driver 改动，输出不变）；官方 nuPlan 配置的 `TORCH_CUDA_ARCH_LIST=8.9;9.0+PTX` 在 RTX 3090（sm_86）上没有可用 kernel，Tokyo 的 smoke 只把这一项改成渲染卡自己的架构（对官方运行的偏离）。

**对方向的含义**：比赛线的「镜像能不能过官方容器条件」不再是未知项；哪个 checkpoint 上场与镜像无关，OT3 出结果后跑一次 `new_tag.sh` 即可。box 上的 public 分数是官方分数在这个数值噪声内的估计，逐 scene 不可预测。
**状态**：**成立**（中）。限定：一台主机一张 3090；每个 driver 路径一个 checkpoint、一个 48-scene 列表；P2H10 的 native 参照不是同列表运行；主办方的 GPU / 驱动版本、runner 的真实 `docker run` 参数、16 replica 同时运行、吞吐预算、ensemble driver 的容器运行都没有验证；`+cu126` 与 `+cu130`、3090 与 6000D 两个因素没有拆开。
**会推翻或推进本条的证据**：用户提交的 `nuplan-warmup` 状态（通过 = 形态被官方环境接受；失败信息指向驱动版本、权限或超时中的哪一个）；同一张卡上 `+cu130` 镜像与 `+cu126` 镜像的 plan 差；4 个实例同卡的 VRAM 与时延。
