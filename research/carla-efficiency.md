# CARLA 闭环评测的效率优化

状态: 独立主题，2026-09-21 立项。不阻塞主线（[frozen-vlm-planner.md](frozen-vlm-planner.md)），
但决定闭环实验**值不值得做**——见 [decisions.md](decisions.md) 第 16 条。

## 为什么单独立题

闭环评测的成本目前是"几小时"还是"几天"没有答案，而这个答案直接决定论文要不要做闭环。
更重要的是：**这件事的优化空间很可能是数量级的，而不是百分之几**，
所以值得当成一个独立的工程问题认真做，而不是顺手调参。

用户的经验判断（本项目的起点假设，需要验证）：
**相机是最慢的一环，而瓶颈在数据管线，不在渲染本身**；内存使用有优化空间；
官方的运行脚本写得不好，在不改变运行原理的前提下有可观的加速余地。
历史上他们做到过 2–3 倍，用过 Cython 之类的编译型辅助手段。

## 已经测到的事实（2026-09-21，RTX PRO 6000，Town10HD_Opt、40 辆背景车、20 Hz 同步）

单实例，相机数与分辨率：

| 相机数 | 分辨率 | FPS | 相对实时 |
|--:|:--|--:|--:|
| 1 | 1600×900 | 28.46 | 1.42× |
| 6 | 1600×900 | 9.62 | 0.48× |
| 6 | 800×600 | 10.48 | 0.52× |

多实例并发（单相机 1600×900，每个实例一个独立 server）：

| 实例数 | 总 FPS | 相对单实例 | VRAM | GPU util | 失败 |
|--:|--:|--:|--:|--:|:--|
| 1 | 28.2 | 1.00× | 6.8 GB | 48% | — |
| 2 | 46.8 | 1.66× | 14.1 GB | 77% | — |
| 4（同时启动） | 74.2 | 2.63× | 26.7 GB | 99% | 1 个 world-load 超时 |
| **4（错开 20 s 启动）** | **86.5** | **3.07×** | 27.5 GB | 94% | 0 |
| 5 | 82.0 | 2.91× | 30.0 GB | 99% | 0 |
| 6 | — | — | — | — | **第 6 个 server segfault** |

**三条已经能下的结论**：

1. **瓶颈是 per-sensor 开销，不是 GPU fill rate。** 像素砍到四分之一只换来 9%。
   所以该砍的是相机数量，不是分辨率——这和"降分辨率提速"这个最常见的直觉相反。
   这一条独立支持了用户"问题在数据管线"的判断。
2. **限制并发的既不是核心也不是显存，而且"上限是多少"取决于配置，不是机器。**
   在**饱和负载**下（单相机 1600×900、每 tick 都渲染）GPU 先到顶：4 个实例 86.5 FPS 是峰值，
   第 5 个净亏（82.0），第 6 个在启动时 `Signal=11 / CommonUnixCrashHandler` segfault。
   但换成**优化后的配置**（800×450、每 4 tick 渲染、Qwen 真的在环），
   4 / 6 / 8 实例是 87.4 / 119.5 / 146.7 tick/s（1.00× / 1.37× / **1.62×**），**零失败，第 6 个不再 segfault**，
   8 实例时才轮到 CPU 到顶（load 23.8/25，显存 59/96 GB）。
   *这一条改写过三次*：最早说"核心是瓶颈"（按单实例 4.5 核/实例外推，方法错的）；
   然后说"上限是 5"（N=5 没测完）；然后说"跑 4 不要跑 5"（只在饱和负载下成立）。
   **现在的说法：先把每个实例的 GPU 负载降下来，上限自己就抬上去了；先调配置，再调实例数。**
   **推论不变：显存最多用到 59/96 GB，这张卡在闭环上仍然过剩。**
3. **启动必须错开。** 4 个实例同时启动时有一个 world-load 超时，错开 20 s 之后不但不失败，
   总吞吐还高 17%（74.2 → 86.5）。同时启动是自己造出来的 thundering herd，
   不是并发上限——差一点就把"3 个实例封顶"当成结论报出去。

## 目标硬件（决定哪些优化值得做）

2026-09-21 定下来的前提：**以后会加到 2–4 张卡，但卡型不换，都是 RTX PRO 6000。**
这对优化方向有三个直接影响：

- **per-card 的优化会被乘以卡数，跨卡的调度只值一次。** 所以先把单卡从 4 个实例榨到更多、
  或者把每个实例榨得更快，比写一个漂亮的多卡调度器更值钱。
  **这一条已经兑现**：降低每实例负载之后单卡从 4 个实例开到 8 个，1.62×，一张卡就拿到了。
- **不要为"换更大显存的卡"做任何设计。** 8 实例时显存也只用到 59/96 GB。
- **多卡的正确形态是按路线分片，不是把一次仿真拆到多卡上。** 220 条路线天然可分，
  `--gpu-rank` 已经在 Bench2Drive 改过的 leaderboard 里。续跑机制必须是**跨卡幂等**的：
  一条路线在哪张卡上跑完都算跑完，重跑时无论落到哪张卡都要跳过。

## 用真实 policy 跑，不要用空跑的仿真器

空跑的 simulator 给出的是乐观假象，因为**推理和渲染抢同一张卡**，不是并排加算力。
盘上已经有 DINOv2-base、SigLIP2、V-JEPA 2、Qwen3-VL-4B，所以这件事现在就能做，不用等数据。
建议按成本从低到高铺一条曲线，每一档都报 sim-time ratio 和 220 条路线的外推：

| 档 | policy | 问的是什么 |
|---|---|---|
| 0 | stub（固定控制） | 仿真器本身的地板，只用来对照 |
| 1 | DINOv2-base 单帧 | 一个便宜 backbone 进环之后掉多少 |
| 2 | Qwen3-VL-4B 中层截断 | **我们真正要跑的那个成本**，见 [frozen-vlm-planner.md](frozen-vlm-planner.md) |

第 2 档是唯一能回答"闭环到底要多久"的数字，前两档是用来定位掉速发生在哪一段的。

## 假设的结论（2026-09-21 全部测完）

完整数据、方法和表格在 [docs/bench2drive-cost.md](../docs/bench2drive-cost.md)。
测量对象是**未经修改的 Bench2Drive 0.0.4 leaderboard 跑真实路线**，
所有插桩和优化都是带开关的 monkeypatch（`scripts/b2d_hooks.py`），未优化路径保持可复现。
噪声带：同一配置测三次是 158.8 / 170.6 / 170.4 ms/tick，**8% 以下的差别不算结果**。

| # | 假设 | 结论 | 数字 |
|---|---|---|---|
| H1 | 时间花在 sensor 从 server 到 Python 的路径上 | **成立，但位置和想的不同** | 3 相机 1600×900：一个 tick 158 ms，其中 **128 ms 是阻塞等相机帧**（79%），Python 侧的解包拷贝只有 12 ms 且与等待并发 |
| H2 | 每 tick 取图是浪费 | **成立，且是最大的那个杠杆** | decimate 2/4/10 → 1.76× / 2.12× / 3.36× |
| H3 | Python 侧的 `frombuffer → deepcopy` 链可消除 | **证伪（对 wall clock 而言）** | 完全去掉拷贝：12.4 ms → 0.13 ms CPU，总时间 158.3 → 165.7 ms，**没有任何收益**。省的是 CPU，不是时间 |
| H4 | leaderboard / scenario_runner 的 per-tick Python 开销可观 | **量可观，收益为零** | 见下面单列一段 |
| H5 | 降低每实例 GPU 负载能把并发上限推高 | **成立，而且比预期多** | 优化后的配置 6 个、8 个实例都跑得干干净净，总吞吐 1.37× / 1.62×。第 6 个实例的 segfault 是**饱和负载下的现象，不是 6 这个数字的上限** |
| H6 | 推理和仿真重叠能藏掉推理 | **成立，几乎全藏掉** | 129 ms stand-in：167.4 → 165.1 ms/tick，tick 里只剩 1.5 ms |

### 两条最重要的、反直觉的结论

**1. 相机的成本是 per-sensor，不是 per-pixel，而且这一次是在真的把图读出来的循环里测的。**
把 3 个相机从 1600×900 降到 400×225（像素 1/16、过网络的字节 1/16），总时间 158.3 → 153.4 ms，
在噪声带里。每多一个相机固定加约 33 ms/tick。
所以**降分辨率救不了你，减相机数或者减帧数才行**——这是 H2 成为最大杠杆的原因。

**2. 照模型的输入尺寸直接渲染，是整套里单笔最大的收益，而且它是免费的。**
因为 CARLA 的 per-camera 成本与分辨率无关，让它直接出 800×450 在仿真侧不要钱；
而 policy 侧省掉了 resize：Qwen3-VL-4B 三相机 **139 ms → 59.9 ms**，DINOv2-base **21.9 ms → 5.3 ms**，
token 数、forward、特征完全一致。
顺带纠正一件我们自己的事：[docs/waymo-e2e.md](../docs/waymo-e2e.md) 里 127–216 ms/frame 是**离线吞吐**，
预处理藏在 DataLoader worker 里；闭环里预处理在关键路径上，占到延迟的 **70%**（DINOv2 是 85%）。
论文里要注明：800×450 直接渲染出来的图 ≠ 1600×900 降采样的图（没有 box filter，aliasing 不同），
训练和评测必须用同一种。

### H4 单列：为什么不写 Cython

`--cprofile` 指向唯一一个热点：scenario_runner 的 `RouteLightsBehavior._turn_close_lights_on`，
**36.8 s 的一条路线里占 5.3 s，71 ms 的 tick 里占 17.8 ms，占总 wall clock 的 14.5%**，
也就是 scenario tree 开销的四分之三。它每个 tick 通过 RPC 把全地图的路灯重新取一遍、
在 Python 里逐个算距离、再把本来就已经是那个状态的灯重新 `turn_on`/`turn_off` 一次。

**所以热点是一个函数，而它花时间的地方是「为不变的数据反复发 RPC」，Cython 碰不到。**
按语义等价的方式缓存掉（`--cache-lights`，同样的灯亮、同样的画面）之后，
**scenario tree 从 25.0 ms 掉到 7.8 ms，3.2×**——而 wall clock 没有变好，还略微变差
（157.9 → 193.4 ms；decimate 配置下 62.3 → 67.6 ms），省下来的 Python 时间几乎 1:1 地
重新出现在阻塞等待里。leaderboard 的 per-tick Python 本来就藏在 sensor 管线后面。

**H4 的天花板在单实例下是 0。** 开关留着，因为 8 实例时 CPU 才是瓶颈，那时省 CPU 可能有用——但没测过，不要假设。

## 真实 policy 进环之后的数字（这是回答「小时级还是天级」的那一栏）

stand-in 用 `time.sleep` 会让 GPU 空着，真模型要和 CARLA 的 renderer 抢同一张卡，所以两个都报。
policy 在独立进程里（CARLA 客户端是 py3.8，torch 是 py3.11），走 unix socket。

| policy | 配置 | ms/tick | 相对实时 |
|---|---|--:|--:|
| 无 | 3 相机 1600×900 | 158–170 | 0.32× |
| 129 ms stand-in | 每 tick | 294.6 | 0.17× |
| 129 ms stand-in | decimate 4 + overlap + zero-copy | 91.9 | 0.54× |
| DINOv2-base | 1 相机，每 tick，1600×900 | 196.6 | 0.25× |
| **DINOv2-base** | 448×252，decimate 4，overlap | **44.5** | **1.13×** |
| Qwen3-VL-4B @L18 | 3 相机，每 tick，1600×900 | 520.9 | 0.096× |
| Qwen3-VL-4B @L18 | decimate 4 + overlap + zero-copy | 85.2 | 0.59× |
| **Qwen3-VL-4B @L18** | **+ 按模型尺寸渲染（800×450）** | **71.1** | **0.70×** |

**把我们的模型直接塞进环里，比认真接进去贵 7.3 倍。**
另外注意 stand-in 藏掉的争抢：Qwen 单独跑是 139 ms，每 tick 跑时是 365 ms/tick，
`sleep(129)` 乐观了 2.8 倍；一旦 decimate + overlap，争抢也跟着消失，两者就差 20% 以内了。

## 220 条路线要多久

实测：**44 条路线、4 个 worker、Qwen3-VL 真的在环里，0.71 小时**（42/44 跑完）。
平均每条 2615 tick、121.7 s，平均 45.8 ms/tick。按 220 条 × 2615 tick 外推：

| 配置 | 实例数 | 总 tick/s | 220 条 |
|---|--:|--:|--:|
| Bench2Drive 原样（3 相机 1600×900、每 tick 推理） | 4 | 5.9 | **约 15 小时** |
| 优化后 | 4 | 87.4 | 1.8 小时 |
| 优化后 | 8 | 146.7 | **约 1.1 小时** |

**同一条路线、同一张卡，优化前后差 13.9×。** 结论那句话：**闭环是小时级，不需要换机器。**

必须同时说的四件事：Town12/13 是 220 里的 151 条、地图大得多（若贵一倍就是 3–4 小时）；
我们的 stand-in 故意开得差，38 条里有 13 条撞到 4000 tick 上限；
6 相机 BEV 模型（UniAD/VAD）大约再贵一倍；以及重启带来的损耗。

## 边界

- **不改变评测语义。** Bench2Drive 的 leaderboard 和 scenario_runner 是改过的（自己拉起 CARLA、
  加了 `--gpu-rank`、加了 4000 tick 上限），换上游版本会让评测跑不起来。
  任何优化都必须保证：同一条路线、同一个 seed，结果与未优化路径一致。
- **每个优化留开关**，未优化路径必须可复现，否则数字没法审。
- **先 profile 再改。** 改某一段之前先说清楚它占总时间的百分之几——那就是这个优化的天花板。
  这条是为了避免"传统上大家都优化这里"式的浪费。
- **稳定性优先于吞吐。** 已知两个问题：Town12 的 sensor-dormancy segfault（220 条路线里 104 条是 Town12）、
  单卡长时间无人值守 hang。**闭环的典型失败是第三小时卡死，不是起不来。**
  能复现或排除其中一个，比再榨 20% 吞吐更有价值。

## 可靠性和续跑（和效率同等重要）

用户的经验：**CARLA 经常断、经常要重启**，所以续跑策略必须先做好，否则吞吐优化没有意义——
一次 220 条路线的评测如果在第 3 小时崩掉、又得从头来，那省下来的 30% 吞吐一次就赔光。

要做到的性质，按重要性排：

| # | 性质 | 具体要求 |
|---|---|---|
| R1 | **崩一条只赔一条** | 每条路线独立进程、独立 CARLA server；一条崩掉不影响其余，更不能拖垮整批 |
| R2 | **断点续跑** | 重跑同一条命令，已完成的路线跳过，只补没跑完的。leaderboard 自带 checkpoint 和 `--resume`，要验证它在**崩溃**（不是正常退出）之后是否真的可用，不能只信文档 |
| R3 | **能区分"慢"和"卡死"** | watchdog 看的是 tick 是否推进，不是进程是否活着。超过阈值没推进就杀掉重启那一条路线，并记录原因 |
| R4 | **结果可合并、可审计** | 每条路线的结果单独落盘，最后合并；重跑覆盖同一条路线时要么幂等，要么显式记录是第几次尝试 |
| R5 | **失败要留证据** | 崩溃时保留 server 日志、最后的 tick 号、路线 id、seed，否则同一个问题会反复出现而查不出来 |
| R6 | **重启次数本身是一个指标** | 报告"跑完 220 条路线一共重启了多少次、哪些路线反复失败"。如果某几条路线永远跑不完，要在论文里如实说明，而不是悄悄丢掉 |

**R6 有方法论意义**：Bench2Drive 的分数是按路线聚合的，
如果失败的路线被静默丢弃，剩下的分数就是在一个被挑选过的子集上算的，不能和别人的数直接比。
这类"评测工程失误"很难被 reviewer 发现，但一旦被发现整篇论文就废了。

## 可靠性：实测结果

机制在 `scripts/b2d_run.py`，**每一条都是用真的把它弄坏来验的，不是读文档**：

- **R1/R3**：跑到一半 SIGKILL 掉某个 worker 的 CARLA server。route 进程**活得好好的**，
  卡在一个 300 s 超时的 RPC 里——看进程活性只会说一切正常。tick 心跳不前进，
  90 s 后被杀掉重试，另外三个 worker 完全不受影响。
- **R2**：SIGKILL 掉整个 runner，再跑一模一样的命令：9 条已完成的被跳过，
  死掉的进程留下的 claim 被抢过来，只有没跑完的那条重跑。第三次跑是空操作。
- **R4/R5/R6**：summary 从磁盘重建，所以续跑之后仍然报得出前一次的尝试次数。

**一次 44 条路线的无人值守运行：0.71 小时，第一遍 38/44，续跑一次后 42/44，重启 12 次。**
然后是这次最值得记的一条：**12 次重启没有一次是 CARLA 的问题，全是我们自己的端口复用。**
traffic manager 的 RPC server 活在**客户端进程**里，一条正在死的路线还占着那个端口，
下一次尝试在 tick 之前就 bind error，而重试又用同一个端口，于是整整卡满一个 watchdog 超时。
两条 worker 槽就这样废掉，分给它们的路线三次尝试后被放弃——而这两条路线换一个 server index
第一次就跑完了。修法是两行：TM 端口取第一个空闲的，失败的 worker 换下一个 server 槽。

**所以稳定性的诚实结论是：在 Town01–10HD 上的 3.5 个 worker 小时里，CARLA 本身一次都没有崩、卡、segfault。**
这是真结果，但范围很窄——Town12 的 sensor-dormancy segfault 够不着（地图没装），
「单卡长时间无人值守第三小时卡死」也没有被这 3.5 小时排除。

**R6 的实例**：如果只看 `routes_finished`，这次会报出一个「38/44 条路线上的分数」，
而这 38 条是按「哪个 worker 碰巧坏了」挑出来的。任何 Bench2Drive 分数都必须同时报重启次数和反复失败的路线。

### 多卡

按路线分片。几个 runner 共用一个 `--out` 目录，各自 `--gpu-rank` 和 `--server-index`；
路线用 `O_EXCL` 锁文件认领，`done/<id>.json` 表示「在任何一张卡上跑完了」，重跑落到哪张卡都跳过。
