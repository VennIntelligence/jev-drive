# CARLA 闭环评测的效率优化

状态: 独立主题，2026-09-21 立项。不阻塞主线（[frozen-vlm-planner.md](frozen-vlm-planner.md)），
但决定闭环实验**值不值得做**——见 [decisions.md](decisions.md) 第 16 条。

## 为什么单独立题

闭环评测的成本目前是"几小时"还是"几天"没有答案，而这个答案直接决定论文要不要做闭环。
更重要的是：**这件事的优化空间很可能是数量级的，而不是百分之几**，
所以值得当成一个独立的工程问题认真做，而不是顺手调参。

用户的经验判断（本项目的起点假设，需要验证）：
**相机是最慢的一环，而瓶颈在数据管线，不在渲染本身**；内存使用有优化空间；
官方的运行脚本写得不好，在不改变运行原理的前提下有可观的加速余地。
历史上他们做到过 2–3 倍，用过 Cython 之类的编译型辅助手段。

## 已经测到的事实（2026-09-21，RTX PRO 6000，Town10HD_Opt、40 辆背景车、20 Hz 同步）

单实例，相机数与分辨率。**注意这是 server 侧天花板，不是闭环速率**：
`carla_bench.py` 的相机回调只把到货的帧存下来，从不阻塞，所以它量的是「server 能多快 step」，
而真正的 agent 会阻塞在 `SensorInterface.get_data` 里等这一 tick 的每一帧都落地。
同配置的闭环口径见 [docs/bench2drive-cost.md](../docs/bench2drive-cost.md)，慢将近 3 倍：

| 相机数 | 分辨率 | server FPS | server 相对实时 | **闭环 ms/tick** | **闭环相对实时** |
|--:|:--|--:|--:|--:|--:|
| 1 | 1600×900 | 28.46 | 1.42× | 92.4 | **0.54×** |
| 6 | 1600×900 | 9.62 | 0.48× | 263.3 | **0.19×** |
| 6 | 800×600 | 10.48 | 0.52× | — | — |

**任何成本外推都必须用闭环那两列。** 早先用 server 列做的 220 条路线外推已经作废。

多实例并发（单相机 1600×900，每个实例一个独立 server）：

| 实例数 | 总 FPS | 相对单实例 | VRAM | GPU util | 失败 |
|--:|--:|--:|--:|--:|:--|
| 1 | 28.2 | 1.00× | 6.8 GB | 48% | — |
| 2 | 46.8 | 1.66× | 14.1 GB | 77% | — |
| 4（同时启动） | 74.2 | 2.63× | 26.7 GB | 99% | 1 个 world-load 超时 |
| **4（错开 20 s 启动）** | **86.5** | **3.07×** | 27.5 GB | 94% | 0 |
| 5 | 82.0 | 2.91× | 30.0 GB | 99% | 0 |
| 6 | — | — | — | — | **第 6 个 server segfault** |

**三条已经能下的结论**：

1. **瓶颈是 per-sensor 开销，不是 GPU fill rate。** 像素砍到四分之一只换来 9%
   （闭环口径独立复现：像素砍到十六分之一只换来 3%）。两个数都落在各自约 7–8% 的噪声带附近，
   所以该读的是「降分辨率几乎买不到东西」这个方向，不是 9% 或 3% 这两个具体值。
   所以该砍的是相机数量，不是分辨率——这和"降分辨率提速"这个最常见的直觉相反。
   这一条独立支持了用户"问题在数据管线"的判断。
2. **限制并发的既不是核心也不是显存，而且"上限是多少"取决于配置，不是机器。**
   在**饱和负载**下（单相机 1600×900、每 tick 都渲染）GPU 先到顶：4 个实例 86.5 FPS 是峰值，
   第 5 个净亏（82.0）。
   **第 6 个实例那个 `Signal=11` 大概率不是并发上限，而是端口复用**——
   2026-09-22 的 Large Map 并发扫描里出现的两次 `Signal=11` 都带着
   `bind: Address already in use`，而真正的上限（N=10）表现为显存到顶，不是 segfault。
   但换成**优化后的配置**（800×450、每 4 tick 渲染、Qwen 真的在环），
   4 / 6 / 8 实例是 87.4 / 119.5 / 146.7 tick/s（1.00× / 1.37× / **1.62×**），**零失败，第 6 个不再 segfault**，
   8 实例时才轮到 CPU 到顶（load 23.8/25，显存 59/96 GB）。
   *这一条改写过三次*：最早说"核心是瓶颈"（按单实例 4.5 核/实例外推，方法错的）；
   然后说"上限是 5"（N=5 没测完）；然后说"跑 4 不要跑 5"（只在饱和负载下成立）。
   **现在的说法：先把每个实例的 GPU 负载降下来，上限自己就抬上去了；先调配置，再调实例数。**
   **这一条 2026-09-22 被 Large Map 推翻了一半**：小地图上显存确实只用到 59/96 GB，
   但 Town12 上每个实例 6.3 GB，10 个实例就是 83.5 GB（峰值 87.4），12 个装不下。
   **「这张卡在闭环上过剩」只对小地图成立。**
3. **启动必须错开。** 4 个实例同时启动时有一个 world-load 超时，错开 20 s 之后不但不失败，
   总吞吐还高 17%（74.2 → 86.5）。同时启动是自己造出来的 thundering herd，
   不是并发上限——差一点就把"3 个实例封顶"当成结论报出去。

## 目标硬件（决定哪些优化值得做）

2026-09-21 定下来的前提：**以后会加到 2–4 张卡，但卡型不换，都是 RTX PRO 6000。**
这对优化方向有三个直接影响：

- **per-card 的优化会被乘以卡数，跨卡的调度只值一次。** 所以先把单卡从 4 个实例榨到更多、
  或者把每个实例榨得更快，比写一个漂亮的多卡调度器更值钱。
  **这一条已经兑现**：降低每实例负载之后单卡从 4 个实例开到 8 个，1.62×，一张卡就拿到了。
- **不要为"换更大显存的卡"做任何设计。** 8 实例时显存也只用到 59/96 GB。
- **多卡的正确形态是按路线分片，不是把一次仿真拆到多卡上。** 220 条路线天然可分，
  `--gpu-rank` 已经在 Bench2Drive 改过的 leaderboard 里。续跑机制必须是**跨卡幂等**的：
  一条路线在哪张卡上跑完都算跑完，重跑时无论落到哪张卡都要跳过。

## 用真实 policy 跑，不要用空跑的仿真器

空跑的 simulator 给出的是乐观假象，因为**推理和渲染抢同一张卡**，不是并排加算力。
盘上已经有 DINOv2-base、SigLIP2、V-JEPA 2、Qwen3-VL-4B，所以这件事现在就能做，不用等数据。
建议按成本从低到高铺一条曲线，每一档都报 sim-time ratio 和 220 条路线的外推：

| 档 | policy | 问的是什么 |
|---|---|---|
| 0 | stub（固定控制） | 仿真器本身的地板，只用来对照 |
| 1 | DINOv2-base 单帧 | 一个便宜 backbone 进环之后掉多少 |
| 2 | Qwen3-VL-4B 中层截断 | **我们真正要跑的那个成本**，见 [frozen-vlm-planner.md](frozen-vlm-planner.md) |

第 2 档是唯一能回答"闭环到底要多久"的数字，前两档是用来定位掉速发生在哪一段的。

完整数据、方法和表格在 [docs/bench2drive-cost.md](../docs/bench2drive-cost.md)。
测量对象是**未经修改的 Bench2Drive 0.0.4 leaderboard 跑真实路线**，
所有插桩和优化都是带开关的 monkeypatch（`scripts/b2d_hooks.py`），未优化路径保持可复现。
噪声带：同一配置测三次是 158.8 / 170.6 / 170.4 ms/tick，**8% 以下的差别不算结果**。

### 两条最重要的、反直觉的结论

**1. 相机的成本是 per-sensor，不是 per-pixel，而且这一次是在真的把图读出来的循环里测的。**
把 3 个相机从 1600×900 降到 400×225（像素 1/16、过网络的字节 1/16），总时间 158.3 → 153.4 ms，
在噪声带里。每多一个相机固定加约 33 ms/tick。
所以**降分辨率救不了你，减相机数或者减帧数才行**——这是 H2 成为最大杠杆的原因。

**2. 照模型的输入尺寸直接渲染，是整套里单笔最大的收益，而且它是免费的。**
因为 CARLA 的 per-camera 成本与分辨率无关，让它直接出 800×450 在仿真侧不要钱；
而 policy 侧省掉了 resize：Qwen3-VL-4B 三相机 **139 ms → 59.9 ms**，DINOv2-base **21.9 ms → 5.3 ms**，
token 数、forward、特征完全一致。
顺带纠正一件我们自己的事：[docs/waymo-e2e.md](../docs/waymo-e2e.md) 里 127–216 ms/frame 是**离线吞吐**，
预处理藏在 DataLoader worker 里；闭环里预处理在关键路径上，占到延迟的 **70%**（DINOv2 是 85%）。
论文里要注明：800×450 直接渲染出来的图 ≠ 1600×900 降采样的图（没有 box filter，aliasing 不同），
训练和评测必须用同一种。

### H4 单列：为什么不写 Cython

`--cprofile` 指向唯一一个热点：scenario_runner 的 `RouteLightsBehavior._turn_close_lights_on`，
**36.8 s 的一条路线里占 5.3 s，71 ms 的 tick 里占 17.8 ms，占总 wall clock 的 14.5%**，
也就是 scenario tree 开销的四分之三。它每个 tick 通过 RPC 把全地图的路灯重新取一遍、
在 Python 里逐个算距离、再把本来就已经是那个状态的灯重新 `turn_on`/`turn_off` 一次。

**所以热点是一个函数，而它花时间的地方是「为不变的数据反复发 RPC」，Cython 碰不到。**
按语义等价的方式缓存掉（`--cache-lights`，同样的灯亮、同样的画面）之后，
**scenario tree 从 25.0 ms 掉到 7.8 ms，3.2×**——而 wall clock 没有变好，还略微变差
（157.9 → 193.4 ms；decimate 配置下 62.3 → 67.6 ms），省下来的 Python 时间几乎 1:1 地
重新出现在阻塞等待里。leaderboard 的 per-tick Python 本来就藏在 sensor 管线后面。

**H4 的天花板在单实例下是 0。** 开关留着，因为 8 实例时 CPU 才是瓶颈，那时省 CPU 可能有用——但没测过，不要假设。

## 真实 policy 进环之后的数字（这是回答「小时级还是天级」的那一栏）

stand-in 用 `time.sleep` 会让 GPU 空着，真模型要和 CARLA 的 renderer 抢同一张卡，所以两个都报。
policy 在独立进程里（CARLA 客户端是 py3.8，torch 是 py3.11），走 unix socket。

| policy | 配置 | ms/tick | 相对实时 |
|---|---|--:|--:|
| 无 | 3 相机 1600×900 | 158–170 | 0.32× |
| 129 ms stand-in | 每 tick | 294.6 | 0.17× |
| 129 ms stand-in | decimate 4 + overlap + zero-copy | 91.9 | 0.54× |
| DINOv2-base | 1 相机，每 tick，1600×900 | 196.6 | 0.25× |
| **DINOv2-base** | 448×252，decimate 4，overlap | **44.5** | **1.13×** |
| Qwen3-VL-4B @L18 | 3 相机，每 tick，1600×900 | 520.9 | 0.096× |
| Qwen3-VL-4B @L18 | decimate 4 + overlap + zero-copy | 85.2 | 0.59× |
| **Qwen3-VL-4B @L18** | **+ 按模型尺寸渲染（800×450）** | **71.1** | **0.70×** |

**把我们的模型直接塞进环里，比认真接进去贵 7.3 倍。**
另外注意 stand-in 藏掉的争抢：Qwen 单独跑是 139 ms，每 tick 跑时是 365 ms/tick，
`sleep(129)` 乐观了 2.8 倍；一旦 decimate + overlap，争抢也跟着消失，两者就差 20% 以内了。

## 220 条路线要多久

实测：**44 条路线、4 个 worker、Qwen3-VL 真的在环里，0.71 小时**（42/44 跑完）。
平均每条 2615 tick、121.7 s，平均 45.8 ms/tick。按 220 条 × 2615 tick 外推：

| 配置 | 实例数 | 总 tick/s | 220 条 |
|---|--:|--:|--:|
| Bench2Drive 原样（3 相机 1600×900、每 tick 推理） | 4 | 5.9 | **约 15 小时** |
| 优化后 | 4 | 87.4 | 1.8 小时 |
| 优化后 | 8 | 146.7 | **约 1.1 小时** |

**同一条路线、同一张卡，优化前后差 13.9×。**

**2026-09-22 实测全集，把上面这个外推修正了：那个「约 1.1 小时」乐观了 2.8 倍。**
全部 220 条、8 个 worker、同一套优化配置逐字复现，**11196 s = 3.11 小时**，
01:17→04:24 一条命令无人值守跑完，exit 0，209/220 条完成，245 次 attempt，633881 个 tick。
乐观的地方正是这张表自己标注过的那一条：**它假设大地图和小地图一样贵。**

（这一段先前写的是「3.0–3.5 小时」和 Town13 152.1 / Town12 106.1 ms/tick，
那是跑到一半时的中间值；下面是跑完之后的最终值，小地图那一栏也换成了**同一轮里重测**的 64.3，
而不是前一天 16 条 base 路线上的 54.5——同一个 session 里量出来的基线才可比。）

| 地图 | 路线数 | 实测 ms/tick | 其中 `world_tick` | scenario tree | 相对小地图 |
|:--|--:|--:|--:|--:|--:|
| 小地图 Town01–10HD（同一轮重测） | 55 | 64.3 | 44–59 | 6–19 | 1.00× |
| **Town11 + Town15** | 14 | **60.4** | 34–56 | 7–21 | **0.94×** |

| Town13 | 47 | **156.8** | 94.5（60%） | **55.9（36%）** | **2.44×** |

**这里有一条比倍数本身更重要的更正：「Large Map」不是那个预测变量。**
Town11 和 Town15 一样是 Large Map、一样流式加载 tile，但它们和小地图一样便宜（0.94×）。
真正贵的只有 Town12 和 Town13 这两张具体的图。以后写「Town12 和 Town13」，不要写「Large Map」；
「Large Map 贵 1.80×」这个合并数字只在「220 条里有 151 条恰好落在那两张贵图上」的意义上成立。
**Town12 + Town13 占 69% 的路线、83% 的 wall clock**，整轮的成本基本只由这两张图决定。

机制：优化配置把 sensor wait 删掉之后（0.03 ms/tick），
**原本藏在它后面的 `world_tick`（tile streaming + decimation 推回来的渲染等待）全部露出来**。
而 **Town13 比 Town12 更贵的那一截主要在 scenario tree 上**（55.9 对 29.2 ms），
也就是 `RouteLightsBehavior._turn_close_lights_on` 每 tick 把全图路灯重取一遍——Town13 的路灯最多。
**这让 `--cache-lights` 重新值得测**：它当初是在小地图单实例上被否掉的（省下的 Python 又回到阻塞等待里），
但现在它是 Town13 一个 tick 的 36%，而且 8 worker 下 CPU 是真的超订（load 中位 31.8、p90 47.0 对 25 核）。

（跑之前预登记的预测是 Town12 1.5×、整轮 2–3 小时；实际 1.65× 和 3.11 小时，方向对，量偏乐观。）

**可靠性：11 条路线跑不完，全部在 Town12/Town13。**
`3048, 11715, 11755, 23687, 23708`（Town12）和 `3785, 3800, 23670, 23695, 24041, 24071`（Town13）。
每条三次 attempt、每次都在全新 server 的新端口段上、每次都在**成功跑了 150–360 s 之后**
`Signal=11 / CommonUnixCrashHandler` 崩掉，日志里没有 bind error。
36 次失败的 attempt **全部**是 `server_died_rc139`，占 24.1 worker-hours 里的 2.17 h（9.0%）。
Town11、Town15 和八个小地图**一条都没失败**。
这是 **Town12/Town13 的 sensor-dormancy segfault（Bench2Drive #235 / carla #7772）第一次在未经修改的
官方 leaderboard 路径上复现出来**——之前一直够不着它。
**所以这台机器上的 Bench2Drive 分数最多是 209/220 条上的分数，而哪 209 条是 CARLA 决定的，不是 policy 决定的。**

**R7 的曲线第一次有足够样本，而它不支持定期回收。** 245 次 attempt 按 server age 分桶：
age 0 的失败率 52%，但那是**选择效应**——一条路线崩了就换 server，所以崩溃路线的每次重试都落在 age 0；
11 条注定失败的路线贡献了 36 次失败里的 33 次。该读的是 age 2–9 那段：127 次 attempt、2 次失败、1.6%，**平的**。
失败是**十一条具体路线的属性，不是 server 跑久了的属性**，所以 `--recycle-routes` 继续关着——
这一次是有证据地关着，不是靠算术关着。

**Large Map 上的并发（Town12，各 24 条路线）**：

| N | ms/tick | 理想吞吐 tick/s | VRAM 中位 | load 中位 |
|--:|--:|--:|--:|--:|
| 4 | 84.5 | 25.3 | 42.1 GB | 17.6 |
| 6 | 84.1 | 37.7 | 54.4 GB | 23.5 |
| 8 | 102.5 | 43.5 | 72.0 GB | 23.0 |
| 10 | 101.6 | 53.4 | **83.5 GB（峰 87.4）** | 27.7 |

**膝盖在 4→6**（per-instance 成本完全不涨，白拿 1.5×）。**10 档是显存先到顶**——
**这是这张 96 GB 卡第一次被真正用满**，每个 Town12 实例 6.3 GB，12 个装不下。
所以「大显存卡对闭环没用」这个早先的推论**只在小地图上成立**，Town12/Town13 上显存才是那个约束。
全量跑选了 8 不是 10：10 快约 23%，但会把显存吃到 87/96 GB，
而同一张卡上 Waymo 特征抽取还在按 burst 要显存。

**梯子里那两次启动 segfault 是端口复用，不是并发上限。** server 日志里写得很清楚：
`LowLevelFatalError ... bind: Address already in use` 紧接着 `Signal 11 caught`——
**CARLA 端口被占不会报错，会直接崩。** 梯子一步接一步复用同一个端口段，上一步的 socket 还在 TIME_WAIT。
这直接把 `docs/carla.md` 里「第 6 个 server 在饱和负载下 segfault」也变成了端口复用的嫌疑对象：
**启动时的 `Signal=11`，在读过 server 日志排除端口之前，不能当成并发上限的证据。**

**Town12 不是整体在挂：62/63 成功。** 唯一失败的是 route 3048，三次 attempt 全挂，
每次都是全新 server、不同端口段、跑到约 155 s 时 `Signal=11`，日志里没有 bind error——
**这是 Bench2Drive #235 / carla #7772 第一次在未经修改的官方 leaderboard 路径上复现**。
R1 的隔离按设计生效了：崩的是那个 worker 自己的 server，另外 7 个毫无感觉；
watchdog 5 s 就发现（没耗客户端那 300 s 的 RPC timeout）；三次之后放弃并换 server index 继续。
**总代价是一个 worker 的 480 s，占整轮 0.5%**，而 3048 会出现在 `routes_never_finished` 里（R6）。

**必须和这个数字一起说的三件事**：
我们的 stand-in 故意开得差，**69 条里有 34 条是撞着 4000 tick 上限跑满的**
（中位 3065 tick，而这些路线物理长度只有约 100 m，正常开完约 330 tick）——
**换成真 policy，平均 tick 数可能掉 3–4 倍，整轮进 1 小时以内**；
这不是优化，是评测语义的一部分，但它是目前 wall clock 里最大的一块。
6 相机 BEV 模型（UniAD/VAD）大约再贵一倍。
这一轮还在和 Waymo 的下载与特征抽取抢 CPU，独占估计再快 15–25%。

## 还没有一个能在 CARLA 里开车的策略（这是 3 小时里最大的水分）

**现在的 `--policy gpu` 是什么**：Qwen3-VL-4B **确实在跑真前向**
（3 相机、800 px、1050 token/帧、L18 早退，和 planner 要用的完全一样），所以**推理成本是真的**；
但特征算完就扔，控制来自一个哑的 waypoint follower——6 m/s 定速、朝 6 m 外的 route waypoint 打方向、
**不看红灯、不看前车**。**这就是一半路线撞满 4000 tick 上限的原因。**

盘上的东西没有一个能直接开：我们自己的 planner 的 head 还在训，而且它输出的是
trajectory vocabulary 上的一条轨迹，**进 CARLA 还缺一个 trajectory → throttle/steer 的 controller**；
Qwen-Drive / AutoVLA / openjev 都是 NAVSIM、WOD-E2E 口径的 planner，没有 CARLA agent 的壳；
Bench2DriveZoo 的 UniAD / VAD 要 BEV ground truth、6 相机加 lidar，成本再翻一倍。

**所以下一步是写那个 controller（PID 跟踪 + 红灯和前车刹车）**，理由不是"让数字好看"：
**无论走哪条路我们都需要它**——我们自己的 planner 输出轨迹，轨迹要变成控制量才能进闭环。
它同时把成本模型修准（现在有相当一部分是在测"一辆开得很烂的车怎么卡满 4000 tick"）。

## Town12：一次被我们自己制造出来的"崩溃"（2026-09-22 结案）

**结论：Town12 没问题，220 条路线全部可用。** 用**未经修改的 Bench2Drive leaderboard**
跑 Town12 的 route 1711，288.2 s / 1283 tick 正常跑完，零重启。
崩溃在我们自己写的 `scripts/carla_bench.py` 里，**但具体是哪一行还没查出来**。
gdb（`-nocrashhandler`）拿到的 backtrace 给出了机制：**spawn-actor 的 RPC 内部触发 dormancy pass
→ `PutActorToSleep` 销毁 sensor → `ASensor::EndPlay` 解引用一个失效的 stream token**。
就是 Bench2Drive #235 / carla #7772。

**照抄官方的 world settings 并不能修好它**——五格全崩：baseline、只加 `spectator_as_ego=False`、
只加 `tile_stream_distance`/`actor_active_distance=650`、以及完整 bundle。
*这一条改写过*：本文档上一版写的是"漏掉了官方 `WorldSettings` 里 Large Map 相关的部分"，
那是在只跑通官方路线、还没做 diff 隔离时写的，**被自己的隔离实验否掉了**。

**唯一没测到的高嫌疑项是操作顺序**：leaderboard 是**先 apply `WorldSettings`、再
`load_world(reset_settings=False)`**；我们是先 load、再 apply。
这和"CARLA 每次 `load_world` 都会静默重置 Large Map 设置"正好咬合——
按我们的顺序，设置可能在 load 之后又被重置掉了。一行的事，但没试。
**这期间给出过的每一个路线数上限（69、116）都是错的，因为量的是我们自己的 bug。**

**为什么值得保留这一段**：过程里死了四个假设——地图加载不了、spawn 净空（H7）、
背景交通 / dormancy、server 未就绪。每一个都**符合观察到的模式**
（Town13 没事、裸加载没事、最重的地图失败），每一个都被配对实验干净地证伪。
原因是那条模式是真的，而真正的成因在一行我们漏掉的设置里，
**所以改 lift、sleep、交通流、分辨率都够不着它**。

**方法论（这一轮真正的产出）**：**先跑一个能工作的参照物，再去解释差异。**
官方 leaderboard 整晚就在盘上，跑一次五分钟就能结案。
插桩（那次给出 36.5 / 41.2 / 44 s 时间线的运行）确实比四个假设都有用，
但它仍然是在调试我们自己的代码，所以"先跑参照物"比"先插桩"还要前置一层。
次级教训：**当一个测量的目标根本不会失败时，这个测量没有价值**——
曾经差点把 lift 扫描打在一格永远不崩的配置上，扫出来必然是"任何高度都不崩"，读起来像净空修好了问题。

**只有读源码才看得见的一条**：官方在**每次 `load_world` 之后都重新施加**
`tile_stream_distance` 和 `actor_active_distance`，注释是
"Large Map settings are always reset, for some reason"——**CARLA 会在载入时静默丢弃它们**。
这条是 Large Map 专有的，而且和"`sensor.other.collision` 也会崩"（dormancy，不是渲染）对得上。

## 别人是怎么起 server 的（Bench2Drive 自己的代码和 README）

用户的提示：去看别人的启动代码。看了之后，**我们和 Bench2Drive 的启动方式有五处不同，
而**其中第 0 行是我们最初漏掉的那一处**（第 1 行已被实测否掉）。

**用户的判断（这是当前最强的一条推理）**：官方代码原则上不应该有问题——
Bench2Drive 的 104 条 Town12 路线是有人跑过、发表过的。
**所以崩溃几乎必然在我们自己的 `carla_bench.py` 里，不在 CARLA 或 Town12 里。**
这把问题从"调试 CARLA"变成"逐条 diff 我们和官方路径的差异"，后者便宜得多。
**决定性的测试是：用未经修改的 Bench2Drive leaderboard（`b2d_run.py`）跑一条 Town12 路线。**
它通过，就结案——bug 是我们的。

| # | Bench2Drive 的做法 | 我们的做法 | 影响 |
|---|---|---|---|
| **0** | 用**完整构造**的 `carla.WorldSettings(..., deterministic_ragdolls=True, spectator_as_ego=False)` | 只设 `synchronous_mode` 和 `fixed_delta_seconds`，**`spectator_as_ego` 留在默认 True** | **Large Map 专有的设置**：`spectator_as_ego=True` 时 spectator 会被当作一个 ego 参与 tile 流式加载和 actor dormancy。在 Town12 上 spectator 和 hero 不在同一处，就会让 tile 和 actor 状态围着两个位置来回变。**这是我们和官方之间最贴近 Large Map 的一处差异**，而且是一行 |
| 1 | 起完 server **硬等 `time.sleep(30)`** 再连 | `carla_server.sh` 每 2 s 探一次 TCP 端口，**端口一开就连** | **值得采纳（README 给的理由成立），但已实测证明它不是 Town12 崩溃的原因**——见下面一段 |
| 2 | `load_world` 失败**重试最多 20 次**（`num_max_restarts = 20`） | 一次失败就算失败 | 他们把「起不来」当成常态，我们当成异常 |
| 3 | 用 **`-graphicsadapter=<rank>`** 选卡 | 没有选卡参数 | README：**CARLA 不受 `CUDA_VISIBLE_DEVICES` 控制**，只认 `-graphicsadapter`；而且映射可能是错位的（4 卡时 GPU1 要写 2、GPU2 写 3、GPU3 写 4）。**以后上 2–4 张卡时这条是必须的** |
| 4 | `find_free_port(args.port)`，README 说**避免小于 10000 的端口**（"<10000 could be unsafe"） | RPC 2000+50i，**TM 8000+50i，全在 10000 以下** | 我们今天那 12 次 TM 端口冲突，可能不只是间距问题，还是端口段选错了 |
| 5 | 不传 `-quality-level`（即默认 Epic） | 显式传 `Epic` | 等价，但注意 issue #4940 / #7675：**`-quality-level=Low` 配 `-RenderOffScreen` 会 segfault**，所以 `b2d_run.py` 的 `--quality Low` 选项是个陷阱 |

另外 README 还有两条和我们已经踩到的坑对上了：
**"CARLA is easy to crash"，官方建议是无限重启直到评测跑完**（正是我们的 R2/R7）；
**`tools/clean_carla.sh` 要反复用，有些 CARLA 进程很难杀干净**。

## 用户的既有经验

- **未优化的复现代码大约 2 FPS。** 这是一个有用的 sanity anchor：闭环口径测到的 6 相机
  263.3 ms/tick（3.8 tick/s）和它同一量级，说明**闭环那套数字可信，而 server 侧那 9.6 FPS
  才是偏离常识的那个**。
- 上一段项目用一套**异步手段**拿到了很高的转速——正是 H6 的方向，已被 overlap 复现
  （129 ms 推理藏到只剩 1.5 ms）。
- **CARLA 的 server 侧经常自己死，所以他们挂的是定期重启方案**（R7），
  但周期不能太密，否则时间全花在中转上（周期怎么定见 R7 下面的算术）。
- 另外两条线索——**spawn 抬高 1.5–2.5 m 只用指定 spawn point**、以及
  **timeout 给少了导致重启没完成**——都已被实测排除在 Town12 这次崩溃之外。
  抬高放置仍然是好实践，脚本已采纳；timeout 不是问题，因为 server 在死之前已经成功跑了 20 个 tick。


## 边界

- **不改变评测语义。** Bench2Drive 的 leaderboard 和 scenario_runner 是改过的（自己拉起 CARLA、
  加了 `--gpu-rank`、加了 4000 tick 上限），换上游版本会让评测跑不起来。
  任何优化都必须保证：同一条路线、同一个 seed，结果与未优化路径一致。
- **每个优化留开关**，未优化路径必须可复现，否则数字没法审。
- **先 profile 再改。** 改某一段之前先说清楚它占总时间的百分之几——那就是这个优化的天花板。
  这条是为了避免"传统上大家都优化这里"式的浪费。
- **稳定性优先于吞吐。** 已知两个问题：Town12 的 sensor-dormancy segfault（220 条路线里 104 条是 Town12）、
  单卡长时间无人值守 hang。**闭环的典型失败是第三小时卡死，不是起不来。**
  能复现或排除其中一个，比再榨 20% 吞吐更有价值。

## 可靠性和续跑（和效率同等重要）

用户的经验：**CARLA 经常断、经常要重启**，所以续跑策略必须先做好，否则吞吐优化没有意义——
一次 220 条路线的评测如果在第 3 小时崩掉、又得从头来，那省下来的 30% 吞吐一次就赔光。

要做到的性质，按重要性排：

| # | 性质 | 具体要求 |
|---|---|---|
| R1 | **崩一条只赔一条** | 每条路线独立进程、独立 CARLA server；一条崩掉不影响其余，更不能拖垮整批 |
| R2 | **断点续跑** | 重跑同一条命令，已完成的路线跳过，只补没跑完的。leaderboard 自带 checkpoint 和 `--resume`，要验证它在**崩溃**（不是正常退出）之后是否真的可用，不能只信文档 |
| R3 | **能区分"慢"和"卡死"** | watchdog 看的是 tick 是否推进，不是进程是否活着。超过阈值没推进就杀掉重启那一条路线，并记录原因。**实测到的代价**：Town12 相机实验里 server 已经 segfault，客户端还挂在 RPC 上把 300 s 超时耗完——每格 5–7 分钟里大部分是在等一个已经死掉的 server。主动探活能把这段全部省掉 |
| R4 | **结果可合并、可审计** | 每条路线的结果单独落盘，最后合并；重跑覆盖同一条路线时要么幂等，要么显式记录是第几次尝试 |
| R5 | **失败要留证据** | 崩溃时保留 server 日志、最后的 tick 号、路线 id、seed，否则同一个问题会反复出现而查不出来 |
| R7 | **主动定期重启 server，不要只在它死掉之后被动重启** | 用户的既有做法：UE4 的 server 侧经常自己死，所以他们挂的是一个**定期重启方案**——跑满 N 条路线（或 N 分钟）就主动回收并重起一个新 server，不管它当时看起来健不健康。这和 R2 的被动续跑是互补的：被动的处理已经发生的崩溃，主动的绕开慢性死亡（内存泄漏、状态累积），而且不用付崩溃本身的代价。**但周期不能太密**，否则时间全花在中转上——这是一个要用实测定下来的参数，不是拍脑袋 |
| R6 | **重启次数本身是一个指标** | 报告"跑完 220 条路线一共重启了多少次、哪些路线反复失败"。如果某几条路线永远跑不完，要在论文里如实说明，而不是悄悄丢掉 |

**R7 的周期怎么定（算术，不是直觉）**：一次回收的成本是 server 启动加 world 载入，
现有实测里 Town12 裸载入 36 s、并发启动要错开 20 s，所以一次回收按 30–60 s 估。
而 44 条路线 4 个 worker 跑了 0.71 h，折合**每条路线约 4 分钟**（单 worker 口径）。
于是：**每条都回收** = 15–25% 的纯开销；**每 5 条回收一次** = 3–5%。
真正该测的是**崩溃率随连续运行路线数怎么涨**——如果第 6 条之后崩溃率明显上升，
那么每 5 条回收一次就是免费的；如果崩溃率是平的，主动回收就只是在付开销。
**先测这条曲线，再定周期。**

**R6 有方法论意义**：Bench2Drive 的分数是按路线聚合的，
如果失败的路线被静默丢弃，剩下的分数就是在一个被挑选过的子集上算的，不能和别人的数直接比。
这类"评测工程失误"很难被 reviewer 发现，但一旦被发现整篇论文就废了。

## 可靠性：实测结果

机制在 `scripts/b2d_run.py`，**每一条都是用真的把它弄坏来验的，不是读文档**：

- **R1/R3**：跑到一半 SIGKILL 掉某个 worker 的 CARLA server。route 进程**活得好好的**，
  卡在一个 300 s 超时的 RPC 里——看进程活性只会说一切正常。tick 心跳不前进，
  90 s 后被杀掉重试，另外三个 worker 完全不受影响。
- **R2**：SIGKILL 掉整个 runner，再跑一模一样的命令：9 条已完成的被跳过，
  死掉的进程留下的 claim 被抢过来，只有没跑完的那条重跑。第三次跑是空操作。
- **R4/R5/R6**：summary 从磁盘重建，所以续跑之后仍然报得出前一次的尝试次数。

**一次 44 条路线的无人值守运行：0.71 小时，第一遍 38/44，续跑一次后 42/44，重启 12 次。**
然后是这次最值得记的一条：**12 次重启没有一次是 CARLA 的问题，全是我们自己的端口复用。**
traffic manager 的 RPC server 活在**客户端进程**里，一条正在死的路线还占着那个端口，
下一次尝试在 tick 之前就 bind error，而重试又用同一个端口，于是整整卡满一个 watchdog 超时。
两条 worker 槽就这样废掉，分给它们的路线三次尝试后被放弃——而这两条路线换一个 server index
第一次就跑完了。修法是两行：TM 端口取第一个空闲的，失败的 worker 换下一个 server 槽。

**所以稳定性的诚实结论是：在 Town01–10HD 上的 3.5 个 worker 小时里，CARLA 本身一次都没有崩、卡、segfault。**
这是真结果，但范围很窄——Town12 的 sensor-dormancy segfault 够不着（地图没装），
「单卡长时间无人值守第三小时卡死」也没有被这 3.5 小时排除。

**R6 的实例**：如果只看 `routes_finished`，这次会报出一个「38/44 条路线上的分数」，
而这 38 条是按「哪个 worker 碰巧坏了」挑出来的。任何 Bench2Drive 分数都必须同时报重启次数和反复失败的路线。

### 多卡

按路线分片。几个 runner 共用一个 `--out` 目录，各自 `--gpu-rank` 和 `--server-index`；
路线用 `O_EXCL` 锁文件认领，`done/<id>.json` 表示「在任何一张卡上跑完了」，重跑落到哪张卡都跳过。
