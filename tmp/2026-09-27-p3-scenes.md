## 描述性读数：openpilot 原生 plan（不进门、不进判格）

同一批帧、同一翻转定义（2 s 纵向速度 v2，null = x⁺ 对 real，配对 = x⁺ 对 x⁻，|Δ| ≥ τ）。I3 的 null 上没有原生 plan 的 τ（`runs/elicitation/i3-exam` 只有 `ridge_late` 与 M-C 考生，decisions / todo 里也没有），所以 τ **借用**各模型自己的 I3 `ridge_late` τ，同时报 |Δ| 的分位数。

| 模型 | null 误翻（借用 τ） | null |Δ| 中位 / p90 / p95（m/s） | x⁺ 对 x⁻ 翻转 | 配对 |Δ| 中位 / p90 / p95 |
|:--|:--|:--|:--|:--|
| Cinque 原生 plan（τ 0.527） | 11.7% [0.9, 29.6] | 0.145 / 0.605 / 0.771 | 6.1% [0.0, 15.7] | 0.038 / 0.229 / 0.633 |
| Lebowski 原生 plan（τ 0.734） | 5.2% [0.4, 13.0] | 0.147 / 0.456 / 0.727 | 2.6% [0.0, 7.8] | 0.028 / 0.154 / 0.290 |

逐场景：null 误翻集中在 p3_004（Cinque 87%、Lebowski 39%）与 p3_001（Cinque 17%）；配对翻转集中在 p3_002（Cinque 48%）与 p3_008（Cinque 13%、Lebowski 26%），其余场景为 0。表与分位数见 `native_plan.csv`。
实现：原生 plan 本来没存。合并读出在门的全部步骤之后，另跑一遍 openpilot 到独立的 `op_streams_plan`（`--arrays temporal plan`），场景 0 是在已有渲染上只重跑 openpilot，没有重训、重渲。
同时重算的 `temporal` 与门用的 stream 逐位比较：30 stream × 2 模型全部 bit-identical（`native_identity.csv`；场景 0+1 在放场景 2–9 之前的技术读出里已先证过一次）。门的数没有动。

## ≥ 60 场景扩量的 GPU 时间估计（未启动，需用户另批）

要补 50 段（010–059）。单卡单场景：训练 55–72 min（含 train.py 自带的训练后全序列评估约 8–10 min，这部分墙钟单线程 CPU 受限），渲染约 1.7 min。
训练进程本身是单核 CPU 受限（约 106% CPU，单独时 GPU 利用率约 55%），所以每卡 2 个场景基本不互相拖；本次 2–3 个同卡的场景是 86–111 min。
估计：每场景约 0.75 卡·h（每卡 2 个），50 段约 **38 卡·h**；5 张卡每卡 2 个约 **8 h 墙钟**，每卡 1 个约 50 卡·h / 10 h。合并读出（index + openpilot + exam + 原生 plan）约 10–15 min。
与 CARLA 共卡会慢 2–4 倍（本次 p3_003 在 G 链 CARLA 旁 142 min，场景 5 降到约 50 迭代 / min），扩量要么拿独占卡，要么把 timeout 从 4 h 放宽。
