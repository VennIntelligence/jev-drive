## 1. 问题

V2（RTB1AR-F-s0 → RTB1ARO-L18-s0，第 339 条）修好了公开集的代价（公开 1491 对 RSG −0.002 [−0.011, 0.007]，被追尾 17），到达时停还在，但仍然偏慢：
公开集里有一批场景它比 RSG 走得短得多（例如 d93e31df 1.59 m 对 4.57 m，c665621f 1.06 m 对 3.4 m，982b57b1 3.08 m 对 4.89 m；日志分别走 17.7 / 5.8 / 12.3 m），
用户看视频判断为「爬行 / 起步慢」（handoff 2026-10-17 第 3 节 A 类）。第 315 条的机制：纵向通道是自身运动趋势的跟随者，plan 的速度被喂进去的自身速度历史带着走，
所以历史慢 → plan 慢 → 下一个决策的历史更慢。

问题：在 V2 的配方上加训练时的历史速度噪声（`rm_train --ego-scale-speed 0.5 --ego-scale-max 0.2`：在 50 % 的模仿行上把喂给模型的速度历史乘 s ~ U[0.8, 1.2]——速度、加速度（× s²）、历史位姿的 x y 同比缩放——
目标仍是人的轨迹，所以 plan 的速度必须来自场景而不是历史的尺度），能不能去掉 V2 的爬行，而且不带来新的代价？

先验证据：ACS2P-L18-s0（RSG-L18 配方 + 同样两个参数，1 000 步）过了开环闸（历史 ×0.8 的 4 s 弧长偏差 −0.62 对 −0.93，dev ADE 0.5301 ≤ 0.5290 + 0.01），
held 460 对 WTCP-L18-s0 均分 +0.010 [−0.003, 0.027]、progress_rel +0.019（`ac_pilot_gate.md`、`ac_held.md`）。那次的底座是 RSG，不是 V2；本臂问的是同一个旋钮在 V2 上。

## 2. 臂

`--init RTB1AR-F-s0 --allow-init`，外加 `--ego-scale-speed 0.5 --ego-scale-max 0.2`。底座 RTB1AR-F-s0 就是 V2 的底座（已含 P0 纵向保持项，续训里没有保持项）。


- 一次只改一个量：两个参数。噪声有自己的 rng 流（[seed, 0, 149]），不动主 batch 的抽样。

读数：每个场景在它出现的每一个读数里都出一行（held 460 @18 与公开 1491 @10；公开读数含全部 34 个，held 只含其中 17 个），每行给 RSG-L18-s0 / V2 / V2AC 的分数、失败类型、progress_rel。
规则（固定在代码里，输出之前）：
- 失败类型（取自 results-summary.json 的指标，顺序检查）：at-fault 碰撞按 front / side / rear 记（front 优先）；offroad；corridor；路线生成失败（route-fail，与策略无关）；
  分数 < 0.98 时：非 at-fault 碰撞（hit，含被追尾）、不起步（日志 > 5 m 而本臂 < 2 m）、barely（走了日志里程的 < 10 %）、crawl（10–30 %）、slow（≥ 30 %）；否则 ok。同时有多个零分原因时用 + 连接。
- 「对」= 分数 ≥ 0.9。相对 V2：V2 错而 V2AC 对且分数高 ≥ 0.1 → fixed；两者都错 → still wrong；V2 对而 V2AC 错且分数低 ≥ 0.1 → newly wrong；两者都对 → still right。
  跨过 0.9 线但分数差 < 0.1 的翻转不算变化（记入原来一侧）。
- 计数按「场景读数」（scene-read）数，分读数报告。同一规则可对任意标签集重算：`nx_regress.py table --tags RSG-L18-s0 RTB1ARO-L18-s0 <新臂> --ref RTB1ARO-L18-s0`。
- 用户视频里看到的是 a = RTB1O-L18-s0（以及 RSG），不是 V2，所以不少场景 V2 已经「对」；这张表问的是 V2AC 相对 V2 动了哪些，不是用户原来点名的错是否还在。
