# 控制器评判规则

状态：规则已定（2026-09-24，与用户讨论后写定）；指标的具体操作化由执行方在 dev 数据上试点后冻结，冻结前不得比较候选。

## 为什么需要这套规则

W2 到 Task 8 说明：在一个和自带执行层一起按 benchmark 调过的模型上，Driving Score（DS）分不出执行层的好坏。TFv6 与作者的 route/target-speed PID（A）是按同一套分数挑出来的，任何新控制器在它上面都处于劣势。[a-defects.md](a-defects.md) 又显示，DS 对驾驶品质（踏板抖动、急加减速、无谓停车）完全不敏感。所以要单独立一套规则，回答"这个控制器是否更好，至少更易用"。

## 原则

**控制器的职责是把给定的 plan 忠实、平顺地执行出来；plan 本身好不好是模型的事。** 因此所有用来评价控制器的指标都要**以 plan 为条件**：衡量的是实际表现和 plan 要求之间的差，而不是原始行为。凡是由 plan 本身造成的现象（例如 target speed 突然跳到 0、策略性的长时间停车），都不算作控制器的问题。

## 三层

**L1 跟踪保真度（主判据，不接模型）。** 用固定的参考轨迹驱动控制器，差异只能来自控制器本身。两种参考都做，结果分别报告：
- **expert 轨迹**：特权 expert（例如 LEAD 自带的 expert）实际开出来的时间参数化轨迹；
- **route oracle**：已有 lateral v2 框架下的路线加速度剖面。
覆盖起步、停车、不同速度、不同曲率、S 弯，加上 GNSS/IMU 噪声和接口扰动（horizon、dt、点的稀疏程度、静止抖动）。指标方向：空间和时间上的跟踪误差、超调与收敛、**额外 jerk**（实际 jerk 减去参考本身隐含的 jerk）、鲁棒性。

**L2 闭环、以 plan 为条件（接真实模型）。** 至少接 TFv6 和 TCP 两个 planner。拆成两类 plan，分开评测，分开出分：
- **可行 plan**：跟踪 plan 的误差；plan 之外的踏板反转（plan 隐含加速度的符号没变，控制却来回切换）；额外 jerk；需求不高时的饱和（plan 要的加速度不大，踏板却打满）；起步和停车的遵从度（plan 要走而车不走，plan 要停而车停不住）。
- **不可行 plan**（在物理上不可行，例如 target speed 瞬间跳到 0）：平顺与安全的取舍，即 jerk 降了多少，同时停车距离、与前车的最小间距是否变差。"忠实执行"与"可行性整形"两种设计在这里各自计分。
相同输入下不同控制器的反应，可以用 shadow control 在同一条轨迹上直接比较，但这只是开环证据，闭环结论要靠真实运行。

**L3 系统结果（只作护栏）。** DS、碰撞、route completion。对每个 planner，只要求**非劣**于它原生的控制器（默认界：DS 不低于原生 3 分，CI 按路线整组 bootstrap），不用来判定控制器好坏。策略性停车时长等纯策略指标只描述，不计入控制器评价。

## 判定

一个控制器被判为"更好"：L1 显著优于对照（原生控制器，以及各自适用的基线），L2 的可行 plan 指标不变差且至少一项显著改善，L3 对所有 planner 非劣。只满足 L1、L2 而 L3 不满足，记为"执行更好但与该模型不兼容"，照实报告。**易用性**另报：同一套参数、不做按模型的重调，能否在所有 planner 上满足上述条件。

## 有效性约束

- 指标定义、阈值和"可行/不可行 plan"的判据，先在 dev 数据上试点，冻结（commit）之后才能比较候选；冻结后不改。
- 候选探索与调参只用 dev 路线/场景；最终比较在冻结后的 held-out 集合上做，配对、按路线整组 bootstrap。
- 不改 TFv6、TCP、LEAD，不重训模型。每个 case 检查不变量，驾驶或 runner 出 bug 立即停。
